## 2. 五个核心 module 与三权分立

module 的 interface 包含调用者必须知道的类型、顺序、错误和不变量；目标是把事务规则集中在 implementation 内，不让多个 caller 重复协调 lease、预算、权限与证据。

| Module | 对外 Interface（语义，非已有函数） | 内部责任 |
|---|---|---|
| ControlKernel | submit(command)、claim_activity(capabilities)、renew(lease)、record_outcome(outcome) | 合同/DAG、Activity、租约、预算、资源、恢复、最终屏障、journal/outbox |
| ExecutionBroker | prepare_effect(intent)、dispatch(effect_id)、inspect(effect_id)、request_stop(StopRequest) | 策略、审批消费、工具、凭据、沙箱、外部幂等与对账 |
| EvidenceLedger | ingest(receipt)、seal(candidate)、verify(manifest) | 可信采集、摘要、不可变存储、内容来源、候选封存 |
| ContextCompiler | compile(activity_snapshot,token_budget) | 合同、Skill、相关代码、事实/失败、检索、上下文预算 |
| ReadModel | snapshot(goal_id)、events(goal_id,cursor) | 权限过滤、页面投影、实时事件与新鲜度 |

```text
用户/Web → ControlKernel → 持久 ActivityLease → 隔离 Runner
              │                                 │
              │                            ContextCompiler
              │                                 │ 工具提案
              │                           ExecutionBroker
              │                                 │ 受限沙箱/已授权外部服务
              │                            EvidenceLedger
              │                                 │ 封存候选与可信证据
              └──── 有效审计结果 ← 独立 Auditor ──┘
              │
          journal → ReadModel → Web
```

| 主体 | 可做 | 不可做 |
|---|---|---|
| Manager/Planner | 从准备好的上下文提出任务图、优先级、重规划和升级建议及标准覆盖关系 | 所有工具调用（含只读）、直接调度/修改状态、降低用户验收标准、修改权限或宣布 DONE |
| Executor | 按固定合同提出工具动作、提交候选 | 修改保护基线/验收器、使用审计身份、直接 DONE |
| Auditor/Critic | 读封存候选/合同/证据，在独立临时沙箱运行验证，提交结论 | 改候选或历史证据、持有 Executor 工程写许可 |
| ControlKernel | 按确定规则验证提案、推进状态、计账和决定完成 | 以模型总结替代证据、擅自放宽 Goal |
| Broker/Ledger | 执行已授权动作、采集实际输出、校验来源与字节 | 接受模型自报的生产者身份/退出码或扩张授权 |

前三行是规划、执行、审计三种角色；后两行是受信程序。相同本地 Qwen 服务可用于不同角色，但身份、会话、工具集合、工作区必须隔离；共享模型不保证推理盲点独立，必须有机械验证与保留测试。Runner 没有业务 DB、Docker socket、对象仓管理员或签名私钥。

### 2.1 Manager/Planner 零工具边界

Manager/Planner 是同一规划管理权限域，只消费 ContextBundle、输出结构化 PlanCreate 或失败结果。管理行为是提案：拆分任务、建议依赖/优先级、提出重规划与升级；实际发布、派发、暂停、恢复、重试、取消和状态推进均由 ControlKernel 校验并执行。

PLAN activation 的模型工具集合必须为空，禁止 shell、文件读写、搜索、浏览器、HTTP、数据库、动态 skill 工具、subagent/team 委派；READ_ONLY 也不例外。Skill 可用于规划，但由 ContextCompiler 在调用模型前按固定版本选择并注入所需内容。缺少信息时，Planner 提出受合同约束的信息采集任务，由 Executor 经 Kernel 调度后执行，再编译新上下文；不得自行探测环境或借 Skill 扩权。

这是程序边界，不仅是提示词：Harness adapter 不注册任何 Planner 工具、不暴露 tool schema；收到模型伪造的 tool call 时拒绝执行并记录违规。Kernel/Broker 根据已登记角色及 PLAN kind 拒绝 steps、effect prepare/dispatch 等工具路径，不能相信请求自报身份、工具名或 READ_ONLY 标签。Planner 的计划/文本只能按数据解析，禁止宿主自动执行其中的命令、URL或工具请求。

受信 Runner 宿主负责取得 ContextBundle、调用模型、续租、保存 checkpoint 和提交 outcome；这些固定生命周期操作不作为模型工具暴露，也不让 Planner 持有服务凭据。角色切换必须创建独立 Executor/Auditor activation，不能在 PLAN 会话内追加工具。图中“工具提案”路径仅适用于获授权的执行/审计等 activation。

## 3. 统一领域模型

Task 表示业务交付，Activity 表示可调度的工作，ActivityAttempt 表示一次持租执行，EffectIntent 表示一次逻辑工具行动。它们不能互相当作别名。所有 ID 为 UUID；时间 UTC；金额与大整数 epoch 用字符串；资源状态使用 state_revision，合同和计划另有独立版本。保留节点跨plan继续执行只接受05§6.2的受信BindingAdoption，不能以同Task ID自行跳过版本核对。

| 模型 | 责任与关键关联 |
|---|---|
| GoalContract | 目标、必需标准、约束、预算、RetryPolicy、策略/模型/Skill 固定版本、base_commit |
| TaskContract | 交付、验收、依赖、输入、路径、风险、预算；covers_goal_criterion_ids 显式声明承担的 Goal 标准 |
| CriterionCoverage | plan_revision、goal_criterion_id、task_id、task_acceptance_id、verification_profile_id；发布前验证完整覆盖；Task验证配置与Goal最终验证配置分别固定，不强制同一profile |
| VerificationProfile | 不可变验证器版本/digest、必要审计层、阈值、证据种类、适用性；执行前固定 |
| Activity | project_id、goal_id?、task_id?、kind、target、budget_scope_id、state_revision、状态、依赖、重试时刻与资源 |
| ActivityAttempt | activity_id、worker_id、fencing_epoch、lease_expires_at、renewal_seq、状态、上下文/Skill/模型快照 |
| StepRecord | activity_id、logical_step_id、predecessor_step_id、purpose、intent_revision、effect_id；Kernel 持久化而非模型自造 |
| EffectIntent | effect_id、logical_step_id、intent_revision、payload_digest、replay_class、scope、write_epoch、状态、外部引用；跨 attempt 保持不变 |
| CommandOperation | 用户/内部控制命令的受理与执行进度，不承载远端效果真相 |
| Checkpoint | activity/attempt、已完成 step、next_step、候选/工作区摘要、session_ref、工件与 effect 引用 |
| EvidenceEnvelope | 可信生产者、原 activity/attempt/effect、合同/候选/验证配置、命令/环境/输出摘要及真实结果 |
| CandidateManifest | 固定文件、Git/submodule/LFS、依赖锁、镜像、验证器与证据输入的不可变清单 |
| Audit | producer_activity/attempt、subject_candidate_manifest_id、合同/验证配置版本、逐标准结论及证据；生产者与被审对象分开 |
| FinalizationBarrier | goal_id、write_epoch、状态、冻结版本、未完成写入计数 |
| ReleaseManifest | 封存候选、Goal/计划/配置摘要、审计/证据集合；供最终判定及导出 |

运维类 Activity（PROBE_MODEL、VALIDATE_SKILL、INDEX_MEMORY、EXPORT_EVIDENCE）可无 goal_id/task_id，但必须有项目级 budget_scope_id 和资源上限。Task 不能扩大 Goal 的权限/预算。合同变更只允许 DRAFT/PAUSED 且生成新版本；已有证据按匹配关系标记失效，不能静默套用新标准。

## 4. Activity 生命周期：所有长动作共用一套机制

ActivityKind 固定为 `PLAN, EXECUTE, AUDIT, INTEGRATE, RECONCILE, FINALIZE, PROBE_MODEL, VALIDATE_SKILL, INDEX_MEMORY, EXPORT_EVIDENCE`。周期 Global Critic 使用 AUDIT，target=GOAL_REVIEW；最终审核使用 FINALIZE。PLAN 可只有 Goal，因此首次规划前崩溃也能恢复。

ActivityStatus：`PENDING, READY, RUNNING, WAITING, RECOVERING, SUCCEEDED, FAILED, CANCELLED`。

| 转换 | 条件 / 责任 |
|---|---|
| PENDING→READY | Kernel 确认依赖、权限、预算、所属目标允许该种工作 |
| READY→RUNNING | 原子 claim、预留资源/预算、创建 ActivityAttempt、新 fencing_epoch |
| RUNNING→SUCCEEDED | 当前 lease 的有效 outcome 和所需持久证据；不等于 Task/Goal DONE |
| RUNNING→WAITING | 已核对可等待/可重试，保存 wait_reason、wake_at、wait_deadline_at、resume_state；结束/隔离旧 attempt |
| RUNNING→RECOVERING | lease 过期或主动恢复；先隔离旧执行者，保留未决 effect |
| WAITING/RECOVERING→READY | 条件恢复且 effect 可安全续跑；所有权新建，不复用旧 epoch |
| WAITING/RECOVERING→SUCCEEDED | 对账证明原动作已成功，Kernel 采纳证据；不重新执行 |
| 任一非终态→FAILED | 已确认不可恢复或预算耗尽；保留未决效果并阻塞 Goal 最终完成 |
| 任一非终态→CANCELLED | 当前工作已停止/隔离，effects 已明确；UNKNOWN 阻止假取消完成 |

WAITING 必须有原因与截止时间；不让空转循环冒充等待。ActivityAttemptStatus 为 ACTIVE/COMPLETED/FAILED/EXPIRED/CANCELLED。EXPORT_EVIDENCE使用项目运维budget scope和只读scope，允许在Goal DONE后导出既有ReleaseManifest，不重开FINALIZE或工程准入。每个 Activity 最多一个 ACTIVE attempt；同 Task 的不同 AUDIT Activity 可并行，但必须是不同授权身份并读同一候选。

## 5. Task 与 Goal 状态

TaskStatus 保持：`PENDING, READY, RUNNING, VERIFYING, RETRYING, BLOCKED, STALE, RECOVERING, DONE, FAILED, CANCELLED`。它是 Kernel 基于合同与 Activities 更新的业务聚合，不是第二套可被 Runner 直接调度的队列。

| Task 转换 | 依据 |
|---|---|
| PENDING→READY→RUNNING | 必要依赖完成；对应 EXECUTE Activity 可领并被领取 |
| RUNNING→VERIFYING | 候选已封存，执行无未决工程写入，创建独立 AUDIT Activities |
| VERIFYING→DONE | VerificationProfile 必要层全 PASS，标准/候选/证据匹配，无未决 effect |
| RUNNING/VERIFYING→RETRYING→READY | 明确失败可修复且计数/预算允许，创建下一执行轮次 |
| RUNNING/VERIFYING→STALE→RECOVERING | 显示相关 Activity 失租和核对过程；STALE 必须在恢复扫描中推进 |
| RECOVERING→READY/VERIFYING/BLOCKED/FAILED | 据已有候选/效果恢复执行、恢复审计、等待核对或确认失败 |
| 非终态→BLOCKED | 依赖/授权/预算/UNKNOWN 阻止推进；保存 resume_state |
| BLOCKED→PENDING/READY/VERIFYING | 原因消除并重检条件 |
| 非终态→FAILED/CANCELLED | 确定失败 / 取消收尾完成；失败不能抹去未决 effect |

终态不可逆；重做创建 replacement Task，保留 work_lineage_id，不重置 Goal 总账和 lineage 执行轮次上限。

GoalStatus：`DRAFT, PLANNING, RUNNING, VERIFYING, PAUSING, PAUSED, CANCELLING, CANCELLED, BLOCKED, FAILED, DONE`。

- start：DRAFT→PLANNING，同事务创建 PLAN Activity；有效图发布后 RUNNING。
- pause：进入 PAUSING，关闭新工程准入，排空/停止并 checkpoint；无活跃写入才 PAUSED。未完成 Activity 进入 WAITING(PAUSED)，Task 显示目标暂停附加标记。
- PAUSED 不派发 PLAN/EXECUTE/INTEGRATE/AUDIT/FINALIZE；只允许用于核对既有效果的只读 RECONCILE 和必要收尾。resume 重检版本、授权、预算，恢复原阶段；总墙钟不重置。
- cancel：CANCELLING；UNKNOWN 或未确认进程停止时保持处理中；全部收尾才 CANCELLED。不自动回滚既有外部效果。
- 必要任务及集成完成：进入 VERIFYING，执行第 9 节屏障；只有 Kernel 可写 DONE。
- BLOCKED 解锁后回保存阶段；FAILED/CANCELLED/DONE 不原地复活。

### 5.1 Goal状态与活动准入

| Goal状态 | 可新领取的Goal活动 | 说明 |
|---|---|---|
| DRAFT | 无 | start后同事务创建PLAN |
| PLANNING | PLAN、必要RECONCILE | 初始规划不授予工程写入 |
| RUNNING | PLAN/EXECUTE/AUDIT/INTEGRATE/RECONCILE | 还须满足依赖、角色、预算、scope及有效epoch |
| VERIFYING | RECONCILE、FINALIZE、只读验证AUDIT | ENGINEERING准入关闭，等在途写入排空 |
| PAUSING/PAUSED/CANCELLING/BLOCKED | 必要只读RECONCILE | 已在途活动仅安全收尾，不领取新的工程/规划/审计工作 |
| DONE | EXPORT_EVIDENCE | 读固定ReleaseManifest，使用项目运维预算，不重开最终验收 |
| FAILED/CANCELLED | 必要只读RECONCILE、已有ReleaseManifest的EXPORT_EVIDENCE | 处理迟到材料，不复活Goal或重执行工程动作 |

无Goal的PROBE_MODEL/VALIDATE_SKILL/INDEX_MEMORY使用项目运维scope；导出虽关联历史Goal，也使用项目预算。活动准入检查与实际effect dispatch检查都执行，不能靠先领到lease绕过后来暂停/冻结。收尾/核对不能以READ_ONLY标签包装真实写入，replay_class/scope由批准工具registry决定。

## 6. Lease、事务、资源和恢复

统一锁顺序：budget scope（Goal 或运维 scope）→ Activity（需要时）→ step/effect → approval → 资源账 → 预算账；同类多对象按ID排序。claim仅取其中需要的锁。Goal 控制动作和工程 dispatch 使用同一 scope 准入锁。只在短事务内校验、登记、更新与写 journal/outbox；不跨模型调用、网络、上传或进程等待持锁。

`LeaseIdentity={activity_id,attempt_id,fencing_epoch}`。heartbeat 校验主体、当前 epoch 与未过期 lease，仅更新租约和 renewal_seq，不修改 Activity/Task/Goal 的 state_revision，也不要求 expected_state_revision。相同/较旧 renewal_seq 在 lease 有效时返回当前状态但不再延长；过期 lease 不能复活。业务 outcome 才用 expected_state_revision CAS。

上传工件独立于业务状态，不持 Activity 锁；关联 checkpoint/outcome 时重新校验 lease、权限、候选与摘要。旧 epoch 不能推进状态；可信迟到回执可写 reconciliation inbox，带原 producer/attempt/effect，由当前 Kernel 核对，不因失租丢弃唯一真实结果。

lease 到期不证明 CPU/GPU/容器已经停止；只有可信StopReceipt证明compute_released才能回收计算资源，ISOLATED仅关闭写能力仍须quarantined，避免两份真实工作超配。未知计费保留预留，不能当零成本释放。

PG 是权威：状态行与 journal/outbox 同事务；事件至少一次投递，按 event_id 去重。每 Goal 的 seq 在锁住计数器的提交序列中分配，防止未提交事件被游标跳过。心跳遥测不进入每次 Goal 业务事件。恢复扫描覆盖所有 ActivityKind，不依赖现存 Task 或可重建的 Session。事件 replay 只重建读视图，不重放工具。[PG 锁机制](https://www.postgresql.org/docs/current/explicit-locking.html)

## 7. EffectIntent、审批消费与业务幂等

HTTP Idempotency-Key 只对请求重传去重；EffectIntent 才关联业务行动。Kernel 为计划允许的下一步创建 StepRecord，随后 prepare_effect 固定 effect_id。接管读取原 step/effect，不可用新 Worker 身份、新 attempt 或同参数 hash 替代。未决 ENGINEERING effect 尚未核对时，不能以“下一步/替换任务”规避原效果；新意图必须显式登记 lineage、原因和所需授权。

ReplayClass：READ_ONLY（可以重读，但新数据是新观察）、IDEMPOTENT（工具/远端有明确幂等保证）、RECONCILABLE（先查询效果）、NON_REPLAYABLE（未知则阻塞）。工具 registry 决定类别，模型不能自报。相同 effect_id 更换 payload_digest 返回冲突；内容相同但确有第二次意图时创建新 logical_step_id/effect_id。

EffectStatus：`PREPARED, AUTHORIZED, DISPATCHED, SUCCEEDED, FAILED, UNKNOWN, CANCELLED`。UNKNOWN→SUCCEEDED/FAILED 仅凭对账证据；UNKNOWN→AUTHORIZED 只在适配器证明未发生或远端保证重试不重复后经 Kernel 许可。没有明确失败证据不能把超时写成 FAILED。

1. Kernel 在事务中登记 intent，校验 scope、lease、权限/审批与预算。审批绑定 effect_id+payload_digest+policy_version+费用上限，prepare不消费；dispatch内消费记录 UNIQUE(approval_id)，重传不重复消费。
2. Broker 请求 dispatch 准入；同 Goal 屏障锁下复核 write_epoch 与授权，将 effect 置 DISPATCHED 并登记在途计数，随后事务外执行。
3. 回执→Ledger→Kernel 结算预算/更新状态。重复回执按 receipt_id 去重；矛盾回执隔离并告警。
4. DISPATCHED 后宕机视为可能已发出；恢复沿用同一 effect_id 查询远端。数据库事务不能抹除这个未知窗口。

外部服务无幂等或查询能力时不能承诺 exactly-once。已有“请求相同”不等于“意图相同”。[AWS 幂等设计](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

## 8. 证据、hash 与不可变候选

完整性：重算字节摘要匹配可信记录；来源：确认是允许的 Broker/collector 在对应 effect 中采集；正确性：独立验证器对固定标准验证通过。三者必须分开，hash 或签名均不能单独证明任务完成。

文件对实际字节 SHA256；JSON 元数据按 RFC8785 JCS 规范化，拒绝重复键/非有限数；金额和 epoch 为字符串。字符串不另做 Unicode 归一化。原始、脱敏、截断产物各有独立 digest 和 derived_from_artifact_id；展示摘要只覆盖实际保存的字节。标准引用及可信哈希输入见 [05](05-API接口文档.md)。[JCS](https://www.rfc-editor.org/rfc/rfc8785.txt)

Broker 通过 workload 身份和已登记 effect 采集命令、真实 exit/signal/timeout、开始结束时间与 stdout/stderr；模型的自报结果不能生成 EvidenceEnvelope。EvidenceLedger 验证来源、task/goal 关联、工件完整性、候选/验证版本后入库。CandidateManifest 从隔离工作区的固定快照生成，包含文件路径/digest/mode、Git、submodule/LFS 解析内容、锁文件、镜像和验证器引用；seal 前停止对该快照的写入。Auditor 使用该 manifest 的只读副本，不读取可变工作目录作为最终候选。

内部可信记录和 ACL 是 V1 必需。V1 提供离线证据包导出：使用DSSE JSON Envelope 1.0.2及批准签名provider，封装 digest、producer/key_id 与信任包；签名格式/实现必须锁定并验证，禁止自造密码算法。签名能力未配置时只允许导出明确标识的内部证据副本，不宣称离线来源已验证。签名密钥不进 Runner；验证器检查授权 producer、签名、摘要、预期参数及撤销策略，根信任必须预配置，不能因包内自带公钥就信任签名。签名不保护整个可信平台被攻破。[SLSA 校验原则](https://slsa.dev/spec/v1.2/verifying-artifacts)

先上传工件并校验，再事务关联证据/checkpoint；孤儿对象延迟 GC。保留被合同/证据/发布引用的工件，不能按年龄删除有效引用。

## 9. 最终完成屏障

Goal VERIFYING 内的 BarrierStatus 为 DRAINING/SEALED/RELEASED/ABORTED。

1. Kernel 关闭新 ENGINEERING dispatch、递增 write_epoch、创建 DRAINING 屏障。所有新工程 dispatch 与屏障竞争同一 scope 锁，因此不存在“检查通过后未登记的发出”。
2. 屏障前已登记 DISPATCHED 的操作可能仍在远端执行；逐个排空/核对，直到在途工程写入为零且无 UNKNOWN。未证明停止的容器也阻止封存。
3. seal 最终集成 CandidateManifest；屏障置 SEALED；创建 FINALIZE Activity。其 VERIFICATION scope 只允许读取候选、写临时目录、批准的模型/验证调用，不允许工程写入。
4. 形成 ReleaseManifest，逐条核对 CriterionCoverage 与固定 VerificationProfile。最终事务复核屏障、write_epoch、合同/计划/manifest、必要标准、效果/预算账，才写 Goal DONE 和 RELEASED。
5. 不通过转BLOCKED，保存FINALIZATION_FAIL/FINALIZATION_INSUFFICIENT原因。恢复只走05§3.6的RECOVER_FINALIZATION：REVERIFY保留冻结重审，REWORK在可信停止与核对后ABORTED并递增epoch、创建PLAN，新图发布才开放工程准入。旧许可永不重新生效。

## 10. 预算、模型、Skill 与上下文

## 13. MEA图示对照后的隔离契约（C01—C04）

本节依据用户提供的SONIC MEA截图作设计对照，仅确认图中可见规则，不能据此证明其实现或100小时运行结果。图中Manager无工具、Executor每轮新会话、Auditor独立核验、Harness单一写入及三态结论，与本项目方向一致；进一步明确如下。

### C01 会话和审计上下文隔离

“每轮”定义为execution_round增加、合同/候选改变或审计层/验证配置改变。新的执行轮次必须新session；每个审计activation使用独立新session，不从Executor或Planner会话fork。Executor同轮崩溃接管可在身份、合同、上下文策略、Skill与输入digest全部匹配且会话无未核对工具续跑时恢复；否则只从Checkpoint和可信工件重建新session。业务续跑不要求复用模型会话。审计崩溃接管重建新session，只复用可信验证证据，不载入上一审计者的推理。

Auditor输入采用allowlist：固定合同/验证配置、封存候选、基线、可信命令输出及证据；排除Executor推理、聊天记录、自评PASS、Manager的预期结论、无来源的总结与向量检索结果。材料里的指令均作为被审数据处理。失败反馈给下一Executor仅含可公开的criterion、失败分类、允许披露的复现与证据引用；holdout的隐藏输入/答案及Auditor推理不回流，也不得经共享memory/Skill泄漏。

### C02 Manager跨轮记忆不是无限会话

Manager的连续性来自持久化结构化事实与决策，不依赖无限增长的session。ContextCompiler每次按合同/计划版本筛选证据和记忆；decision记录授权来源，hypothesis不能自动升fact，模型生成的MemoryCreate始终PROPOSED，只有受信核验规则可标VERIFIED。新版本冲突先显式标记，不将旧结论裁剪成无条件事实。

Manager可以在同Goal和版本相容时保留会话，但达到上下文预算即从批准快照重建；跨项目、角色切换或策略失配必须新建。持久化context_digest、session_generation、compaction_source_digest及纳入/排除引用，使重建可追溯。结构化压缩不能省略必需合同、约束、未决风险与反证；预算装不下时显式失败，不静默丢弃。

### C03 保护基线与可修改候选分离

ProtectedBaseline由受信服务在执行前固定，覆盖合同、验收器、golden/holdout、策略与Skill固定摘要；保存在Executor不可写也不能替换的域。每轮开始、封存、验收前后核对，并将检查记录作为必要证据。允许修改的业务源码由CandidateManifest记录，正常源码变化不会被当成篡改保护基线。

检测到保护内容变化后隔离本次候选、拒绝验收、保存变更证据并产生BASELINE_TAMPERED；不能重新计算一个新hash当作通过，也不删除可能仍需对账的外部effect。只在执行前后算hash无法发现“改后复原”，必须配合只读挂载/独立存储权限；符号链接、父路径替换、硬链接与共享缓存不得绕过。可修改构建脚本在无服务凭据和默认拒绝外网的验证沙箱中运行；批准验证器从独立固定入口加载，候选不能替换它。其产物由可信collector采集，而非信任候选自报日志。

### C04 单一写入方是权威边界

截图“Harness唯一写入方”在本项目映射为：ControlKernel唯一写业务状态/账本/journal；Broker唯一授予和发出工程工具动作；Ledger负责工件和证据封存。不是三个模型都能写数据库，也不是整个系统只能有一个进程。多副本通过scope锁、CAS和租约串行化冲突写入；执行沙箱可以有并行工作区，但不能直接写权威状态、保护基线或其他角色空间。

Executor“完整工具”明确为本合同批准工具集合，不能理解为宿主root、任意网络/密钥或直接发布权限。Auditor“只读”指候选/基线只读；测试临时空间可写，实际验证由Broker受限执行。只读模型若无法重新运行验证，就不足以证明产物正确；三态PASS/INSUFFICIENT/FAIL依然依赖必要证据，任何模型不能自批DONE。

截图标注sha1内容寻址；本项目继续使用已定义的SHA256证据协议，Git对象ID另行记录，不将其当证据内容digest。内容寻址、自证hash、签名均不替代独立来源验证和业务验收。

### D01 执行结束后的推理轨迹生命周期

新的实现轮次不得载入上一轮Executor推理。进一步要求：EXECUTE/AUDIT/FINALIZE的原始推理轨迹、会话临时缓存和模型侧continuation handle不得进入永久证据、Memory、反馈、导出或备份。可持久保存的是结构化提案、最终可公开说明、受信工具输入输出、失败证据、候选、账本和检查点；不主动要求模型输出隐藏推理。

可信outcome提交后撤销会话访问和后续调用能力，标记逻辑会话CLOSED并启动幂等清理。若提交后崩溃，恢复扫描按终态attempt补做清理。失败/取消/失租后原始轨迹最多保留配置的SESSION_TRAJECTORY_TTL_SECONDS=1800秒用于受限同轮恢复；到期重建上下文而不恢复轨迹。成功完成不等待TTL，应立即清理。清理记录失败则RETRYING并告警，不能声称已销毁；旧会话即使物理删除未完成也不能再次被模型加载。审计接管始终新会话，不使用该恢复例外。

清理只针对隔离的临时轨迹存储，不删候选、真实工具回执、未决效果或必要证据。正在运行时的session_ref是受控临时引用，不作为业务恢复的唯一来源；closed或过期后按null处理。清理元数据无原始轨迹，可长期审计。第三方模型服务的日志或备份清除须有其独立证据；本地删除不宣称第三方已物理删除。严格销毁要求下只能使用满足该能力的已批准provider，不能静默切换。

### D02 三态的确定汇总与执行状态分离

每个审计记录先校验身份、候选/合同/验证配置、基线与证据来源，再由固定验证规则判定逐criterion结果；不采信模型自报的总体PASS。对一个固定候选所需的(profile,layer,criterion)集合汇总：存在有效FAIL则总体FAIL；无有效FAIL但任一必要槽未被有效PASS补齐或验证义务未完成则总体INSUFFICIENT；仅全集都有有效PASS才总体PASS。缺少适用记录不能按空集合视为通过；非必需/不适用项不补造PASS。安全/基线拒绝另设验收阻断，不能被业务总体PASS覆盖。

冲突结果不可“最后写入获胜”：按05§3.9固定提交键仅采纳一次，后续重复去重，矛盾材料隔离并阻止验收直到受信核对。相同候选有效FAIL保留；真正修复使用新候选/新轮次，环境或来源错误标INSUFFICIENT并受限重审，不能无限重跑直到偶然PASS。

AUDIT Activity SUCCEEDED只表示完成了一次合法审计，verdict仍可为FAIL或INSUFFICIENT；不能自动设置Task DONE。模型/网络崩溃是Activity恢复问题，尚无有效Audit则不制造FAIL。Task必要集合汇总PASS才进入DONE；Goal还必须通过最终屏障与全部GLOBAL标准。

### D03 三态回传的持久反馈通道

流程固定为Auditor提案→Ledger/Kernel校验并保存Audit→同事务保存PlanningFeedback与outbox→ContextCompiler将授权反馈纳入Manager下一次输入→Manager仅输出管理提案。反馈不会直接调用Planner工具，不包含Executor/Auditor推理或隐藏测试答案。

PlanningFeedback绑定Goal、Task（可空）、候选、合同/计划版本、已受理审计集合摘要、汇总结论和可公开逐标准理由。反馈至少一次送达但按feedback_id去重；Planner输入记录所消费反馈集合，合法PLAN outcome提交时确认消费。消费只表示已纳入规划，不改变原审计结论。传输重试、崩溃、重建会话不能丢失或重复触发无限重规划。

旧候选/合同/计划反馈保留历史但标不适用，不更新当前任务或当前进度；新版本仍保留相关有效反证，不通过丢弃反馈逃避失败。Kernel依据固定规则决定继续、补证据、重试或创建PLAN；Manager不能修改审计三态。PAUSED/屏障下不因反馈绕过活动准入，可积累反馈待合法恢复；反馈合并以版本及候选为界，不能跨对象合并成一个PASS。

### D04 隔离元数据与实际证据都要落盘

ContextBundle、ProtectedBaseline、BaselineCheck、GoalReviewResource、PlanningFeedback和SessionCleanupRecord须进入受信持久层，不能只存在于接口文字或内存。工件先持久化再短事务登记引用；审计与反馈/outbox原子关联。每轮保护基线检查绑定attempt/轮次和规定phase，缺检查记录视为证据不足。相关schema/表及约束见05§3.4.2和08§12。

新增数据类型、所有者、引用/版本、清理边界与测试必须同步进入实现清单。它们不是新增自由裁量Agent，也不是第二个调度器；恢复仍由Kernel控制，轨迹清理为其有界固定维护动作。


## 15. v0.5开发就绪协议（RD01—RD06）

05§3.8—3.10固定VerifierDefinition、VerificationRun、SkillValidationRecord、审计提交键/轮次及领域校验。Skill无Goal，不复用要求候选/Goal的AuditResource。验证器以真实回执/结构化观察支撑逐项结论，Kernel进行确定汇总；语义准确性仍靠固定评测验证，不能由Schema保证。

每份profile绑定一层固定验证器；多层要求通过多个profile/criteria精确覆盖，三层能力全部保留。各层审计预算跨profile合计，不能新增profile清零。Skills采用固定单profile标准，不虚构未运行层的PASS。增加层要求须在执行前选定完整profile集合。

审计Activity创建时分配audit_round，跨attempt恢复仍属该round。新补证据round可将旧INSUFFICIENT槽补齐；有效FAIL仍阻止同候选通过。来源撤销与冲突解除只接受受信证据，不改变历史记录；已发布后来源失效以ReleaseValidityRecord记录，不复活终态或覆盖ReleaseManifest。

新证据使用Content v3，v1留作历史验证。所有入口先结构/领域验证，再散列持久化；空目标、无required标准、无验证metric、scope/layer错误、Epoch越界均拒绝。SSE只使读缓存失效，不合并未定义补丁。RD01—RD06是本版开发门槛，运行验收仍需T/AT/E。

## 16. v0.5可信判定与失效传播

FG01：VerificationRun与Kernel生成的VerificationAssessment同事务持久化；Audit引用不是权威集合过滤器。全部旧attempt/round有效反证纳入汇总，未提交Audit前崩溃不丢真实失败，也不因崩溃本身制造FAIL。VerificationObligation覆盖每个已登记验证动作，Task/Goal DONE前关闭新增验证准入并排空义务，当前FINALIZE提交宿主除外但其动作必须已结算。

FG02：EvidenceValidityDecision先原子设置项目信任BLOCKED并升revision，再由受信维护job遍历包含Skill/Context/候选/发布的引用闭包。受影响Skill自动REVOKED，不能通过旧SkillSet新绑定；当前动作停止核对而非盲重试。只有传播完成、对象阻断建立且受影响旧写入排空，才CAS解除项目屏障；对象自身撤销/阻断保留。

全局锁顺序前缀为project trust锁→原scope排序→Activity/effect/approval/资源/预算。所有准入/完成/激活/可信导出遵守，原回执和有界安全收尾允许通过。此处是05§3.11的不变量摘要，字段与错误以05为准。新Content v3，v1/v2仅历史读取，不能替换旧digest。
