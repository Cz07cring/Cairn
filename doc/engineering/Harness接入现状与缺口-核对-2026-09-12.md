### 3.2 上游构建的真实顺序（本轮踩坑记录）

**不是**直接 `git clone && pnpm install` 就能出 `vendor/cordis/lib/index.js`：

1. `install` 只装依赖，**不产出** vendor JS 产物；
2. `tsc -b vendor/cordis/tsconfig.json` 只产**类型**（`outDir: lib/types`），不产 JS；
3. `tsdown` 是真正的打包器，但其配置**自身 import** `packages/typert/generator/lib/types/tsdown-plugin.js`
   —— 该文件也需先构建 ⇒ **鸡生蛋**，表现为
   `Failed to load the config file: Cannot find module .../tsdown-plugin.js`；
4. 正确入口是上游脚本链：`build:lib:host` = `tsc -b tsconfig.host.json && tsdown --env.DSH_BUILD_FACE host`
   —— `tsconfig.host.json` 通过 **project references** 触发整张 host 图的 composite 构建，
   从而先产出 typert 等插件产物，tsdown 才可加载。

> **给后来者的提醒**：遇到 `tsdown` 报 config 加载失败，**不要**去改 config 或手工造插件文件 ——
> 那是缺 `tsc -b` 前置，直接跑上游 `build:lib:host` 即可。

### 6.1 结论先行：我（Hermes）的并行实现已撤回

我在 `apps/runner/src/harness/pin.ts` / `pinGate.ts` 独立做了「钉扎外部可配 + 声明式 pin 文件

### 6.2 Cursor 方案要点（供后续引用）

- `resolveHarnessPin()`：`RING_HARNESS_PIN` 覆盖仓库默认；非法 SHA 失败关闭（不回退最新）。
- `hotSwapHarnessRuntime()`：改 env → `registry.reload()`，带 generation 追踪新旧版本。
- 其头注释明确禁止 query cache-bust 同路径热更 —— 见下节，与我的实测结论一致。

### 6.3 ⚠️ 实测失败模式：query cache-bust 会静默破坏工具注册（已被两方独立确认）

**动机**：Node 的 ESM 按 URL 缓存。长驻 worker 里即使磁盘产物已换新，
`import(同一 URL)` 仍命中缓存 → 新版本不生效。故尝试把生效 pin 作为 query 拼进入口 URL。

**实测结果**：官方 AgentLoop 测试立刻失败：

```
OFFICIAL_LOOP_NO_TOOL_EXECUTION: AgentLoop 未调用 read_file
```

**根因**：上游是多包互 import 结构（`packages/core/agent-loop` 等内部按相对路径引用
共享依赖）。只给**入口**加 query，会使入口实例化的 Cordis Context 与共享依赖内部那份
**不是同一模块实例** → 插件注册不进同一 Context → 工具静默不注册。

**两条独立证据**：① 我今日实测复现；② Cursor `hotSwapHarnessRuntime.ts` 头注释已写明
「禁止用 query cache-bust 同路径热更（会 ESM 双实例导致工具未注册）」。

**结论**：该手法把「换新版本」变成「静默失去工具能力」，比崩溃更危险。**已回退**
（现已确认 `cordisBootGate.ts` 与 origin/main 逐字节一致，无残留）。
正确做法是进程内 registry 重载（Cursor 已实现）。
