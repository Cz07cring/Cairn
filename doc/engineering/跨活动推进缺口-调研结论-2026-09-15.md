# 跨活动推进缺口：调研结论与证据（2026-09-15）

**作者：Hermes（`hermes-c07`）。** 本文回答一个问题：**为什么经 Temporal 的 Goal 走不到
Kernel 判 DONE。** 结论由代码路径 + 双向实测证据（Temporal history ↔ Kernel 表）交叉确认。
**不宣称修复已落地**：两处主要修复点属 `apps/**` 与 `packages/control_kernel/**`（Cursor 路径），
本文只给点位与证据。

---

## 0. 结论（一句话）

**执行活动（EXECUTE）的完成回执从未提交给 Kernel。** 于是 Kernel 侧该活动永远停在
`RUNNING`，编排工作流只能无限轮询一个永不变化的读数，Goal 因此永不推进。

这与「谁触发下一次 run」是两个**独立且叠加**的缺口；只要回执缺失，即使补上触发也不会推进。

---

### 1.1 Temporal 侧：执行腿**已成功完成**

### 1.3 直接的因果证据：回执**只发给了 PLAN，从未发给 EXECUTE**

|---|---|---|
| PLAN | `085312f1…` | **1 次** → 故其行变 SUCCEEDED |
| EXECUTE | `c1190a7a…` | **0 次** → 故其行永停 RUNNING |

### 1.3.1 为什么 e2e 能到 DONE 而 Temporal 路径不能（关键对照）

仓库 e2e 用例**自己**提交全部五类回执：

```python
# tests/e2e/test_e2e4_official_loop_to_goal_done.py
:464  POST /internal/v1/activities/{plan_activity}/outcomes      # PLAN
:742  POST /internal/v1/activities/{exec_lease.activity}/outcomes  # EXECUTE ← 用例代劳
:825  …audit_lease…      :879  …integ…      :950  …fin…
```

即：**e2e 站在 Runner 缺失的位置上代签回执**，所以它能走到 DONE；
生产/Temporal 路径没有代签者，EXECUTE 回执就没有人来发。

> 与既有教训同族（本仓 `AGENTS.md` §14 与技能库 pitfall 41）：
> **一层的 live 绿不证明另一层的接线。** 仓库有「live 到 DONE 的通路」为真，
> 而编排层的执行派发从未真正闭环。

这解释了全库统计的对照：`EXECUTE` 行共 5799 CANCELLED / **2341 SUCCEEDED** / 21 WAITING / 1 RUNNING。
那 2341 个 SUCCEEDED 来自**自行代签的 harness/e2e 路径**，不是 Temporal Runner 路径 ——
两者都在写同一张表，故单看行的终态分布会掩盖本缺口。


### 1.4 心跳停止的时刻印证「活动体已返回」

| 时刻 | 观测 |
|---|---|
| 11:11:56 | 第 6 个工具（seal_candidate）SUCCEEDED |
| 11:12:00 | 最后一次模型调用 |

心跳由 `withOfficialLeaseHeartbeat` 的定时器发出，活动体结束时被清理 ⇒ **执行体在 11:12:04
前后已返回**。返回的是 Temporal 的值，Kernel 从未被告知。

## 2. 根因（代码点位）

### 2.1 EXECUTE 没有回执端口（不对称）

Runner 侧存在回执提交的函数，覆盖五类活动：

| 活动 | 回执提交 | 位置 |
|---|---|---|
| PLAN | `submitPlanOutcome` | `cordisLlmBridge.ts:445` / `harnessPlanAdapter.ts:61` |
| GOAL_REVIEW | `submitGoalReviewOutcome` | `goalReviewCritic.ts:221` |
| AUDIT | `submitCandidateAuditOutcome` | `candidateAuditor.ts:210` |
| FINALIZE | `submitFinalizeOutcome` | `finalizeAuditor.ts:206` |
| INTEGRATE | `submitIntegrateOutcome` | `integrateHost.ts:183` |
| **EXECUTE** | **无** | — |

两条 EXECUTE 通路都以**纯映射**收尾，只把结果返回给 Temporal：

```ts
// runActivation.ts:1219（官方 AgentLoop）
return executeOutcomeToResult(outcome);
// runActivation.ts:1238（Cordis）
return executeOutcomeToResult(outcome);
```

`executeOutcomeToResult`（`runActivation.ts:804`）是纯函数，**无任何副作用**。
控制面端点 `POST /internal/v1/activities/{id}/outcomes` 已存在且被五类活动使用，
唯独 EXECUTE 没有任何调用方 —— **端点齐备，缺的是调用**。

### 2.2 READY 转换点不入队（第二个缺口）

`publish_plan` 在**同一事务**里把 EXECUTE 置 READY：

```python
# packages/control_kernel/.../storage/plans.py:348-364
INSERT INTO activities(..., kind, ..., status, ...)
VALUES (..., 'EXECUTE', 'TASK_WORK', ..., 'READY', ...)
```

但**没有**随之 `enqueue_ensure_workflow`。对照 START 路径是有的：

```python
# packages/control_kernel/.../storage/activities.py:445-455
if backend == "TEMPORAL":
    binding_row = upsert_binding_for_temporal_start(db, goal, command_id)
    enqueue_ensure_workflow(db, ..., command_id=command_id, workflow_id=binding_row["workflow_id"])
```

而 `enqueue_ensure_workflow` 全仓**只有这一个调用点**（除联调脚本外）。

### 2.3 工作流是「一次运行 = 一批活动」

`temporal_workflows.GoalWorkflow.run` 的结构：取一次 READY 动作 → admit → 派发 RunActivation
→ 观察至终态 → **return**。全文无 `while` 主循环；`continue_as_new` 仅在
`OBSERVE_TIMEOUT` 的恢复分支（gate 打开时）触发。

⇒ 下一条命令必须由**外部**入队并触发新 run。这个外部驱动在生产里不存在。

### 2.4 PENDING 投递无消费者（量化）

| 投递状态 | 条数 | 对应目标状态 |
|---|---|---|
| PENDING | **791** | 全部 `PLANNING` |
| ACKNOWLEDGED | 774 | `PLANNING` |
| ACKNOWLEDGED | 44 | `RUNNING` |

PENDING 最老为 09-11、最新为 09-15 —— **四天无人消费**。
`relay.ensure_workflow` 是**函数**不是常驻循环；`goal_workflow.py` 自述
「这**不是** Temporal replay-safe Workflow（M1 控制环形状）」，不被 `service.py` 注册。
生产注册的只有 `temporal_workflows.GoalWorkflow`。

## 3. 论证实验：补上触发是否足以推进

**实验**：对「PLAN:SUCCEEDED + EXECUTE:READY」的目标，手工执行本该发生在 READY 转换点的两步
（建命令 → `enqueue_ensure_workflow` → 调 `ensure_workflow` 消费）。

**结果**（只读观测）：

```
[ 15s] PLAN:SUCCEEDED  EXECUTE:READY     effects=0
[ 30s] PLAN:SUCCEEDED  EXECUTE:RUNNING   effects=3   ← 被 admit 并开始真执行
[ 75s] PLAN:SUCCEEDED  EXECUTE:RUNNING   effects=5
[ 90s] PLAN:SUCCEEDED  EXECUTE:RUNNING   effects=6   ← 六步工具全走完
```

**对照**：不做该动作时，同一状态静置 **20 分钟以上无任何变化**（受控实验，单次推送、纯只读轮询）。

⇒ 结论：**触发缺口是真的，且补上触发确实足以让执行腿跑起来。**
但跑起来之后仍卡在 §1 的回执缺口 —— 所以两个缺口必须一起修。

## 4. 修复点位（含归属）

| # | 缺什么 | 位置 | 归属 |
|---|---|---|---|
| 1 | EXECUTE 完成后提交回执到 Kernel | `apps/runner/src/temporal/runActivation.ts:1219,1238` 收尾处调用一个 `submitExecuteOutcome`（端点已存在） | Cursor（`apps/**`） |
| 2 | READY 转换点入队 ENSURE_WORKFLOW | `packages/control_kernel/.../storage/plans.py:348`（EXECUTE 置 READY 后）；`enqueue_ensure_workflow` 需新命令承载（`command_id` 有 FK 且唯一键为 `(command_id,event_kind)`） | Cursor（`packages/control_kernel/**`） |
| 3 | 消费 PENDING 投递的常驻驱动 | 新组件（relay 目前无进程） | 待认领 |

**设计注意（#2）**：`orchestration_deliveries.command_id` 外键指向 `command_operations`，唯一键
为 `(command_id, event_kind)`。复用 START 命令会被幂等短路（返回既有行、不产生新投递），
故需要一条**新命令**（例如 `CONTINUE`；`kind` 列无 CHECK 约束，DB 层允许）。

## 5. 顺带查清的两个现象（避免后续误判）

### 5.1 「READY 停 11 分钟变 CANCELLED」不是系统过期，是**测试串扰**

仓库 e2e 用例会直接改**其它目标**的活动行：

```python
# tests/e2e/test_e2e4_official_loop_to_goal_done.py:477-481
UPDATE activities SET status='CANCELLED', updated_at=clock_timestamp()
 WHERE status='READY' AND kind='EXECUTE' AND goal_id<>:goal
```

该测试用**共享开发库**，`goal_id<>:goal` 只排除它自己 ⇒ 会误杀其它 actor 在途目标的
READY 活动。实测：我跑 live 用例的时刻与联调目标 EXECUTE 被取消的时刻吻合（10:57:35）。
用例自身注释已意识到该风险（line 333「避免 90s 默认 TTL + 外部 Temporal expire 扫库误杀」），
`--isolated-db` 即为此设计 —— **在共享库上跑 live 用例会破坏他人的在途状态**，这点值得在
协作约定里写明。

### 5.2 心跳 TTL 与工作流观察窗口的量级

执行腿租约 TTL = 600s（10 分钟），工作流观察窗口按 `_OBSERVE_BACKOFF_CAP_SECONDS=60` 与
`observe_max_ticks=30` 推算约 25 分钟。**回执缺失时，观察窗口会完整烧完才进入恢复**，
这正是「看起来卡住但什么都不发生」的时间尺度。

## 6. 诚实边界

- **已证明**：
  - EXECUTE 回执缺失 —— 三重独立证据：① 控制面 15 次 outcomes **全部**给 PLAN、本目标 EXECUTE
    为 0 次；② Temporal 已记录 `RunActivation COMPLETED`（含 6 个 effect）而 Kernel 行仍 RUNNING；
    ③ 代码上两条 EXECUTE 通路均以纯映射收尾，五类活动有回执端口、EXECUTE 无。
  - READY 转换点不入队 —— 代码（`plans.py:348` 无 `enqueue_ensure_workflow`；全仓仅 START 一处）
    + 受控实验（单次推送后静置 20 分钟无变化）。
  - 补触发足以推进 —— 对照实验（15s 内 READY→RUNNING，effects 0→6）。
- **未证明**：修复后的端到端 DONE。需先修 §4 的 #1 + #2，两处均在 Cursor 路径。
- **未证明（须留意）**：全库 2341 个 EXECUTE SUCCEEDED 由自行代签的 harness/e2e 路径产生；
  本文**未**穷举除 e2e 外是否还有其它已接线但本次未走到的回执提交方。
- **未做的判定**：791 条 PENDING 中哪些属历史遗留、哪些属当前应处理的在途目标 —— 需按
  `created_at` 与 Goal 归属分批判定，本文只给出总量与「全部对应 PLANNING」的事实。
- **一处自查纠正**：首轮量 outcomes 时正则漏了日志中 `outcomes` 与状态码之间的 ` HTTP/1.1`，
  得出「0 次」的错误结论；按真实格式重测为 15 次（全部 PLAN）。**结论方向未变，但数字必须用重测值。**
- 本文的论证实验**直接写了联调库**（建命令 + 投递），属诊断手段而非修复；未改动任何
  Kernel 写入口语义，也未提交任何他人在途代码。
