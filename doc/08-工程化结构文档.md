# 工程化结构文档

> V1开发规格v0.5。现有仓库是文档项目；以下源码、迁移、脚本和服务均待实现。五个module与协议分别见[01](01-开发文档.md)和[05](05-API接口文档.md)。

## Planner 运行隔离要求

PLAN activation 只接收固定 ContextBundle 并输出结构化规划结果，模型工具注册表为空；不挂载工程工作区、不持有工具/服务凭据。受信宿主使用固定生命周期客户端续租和提交结果，不能成为模型请求的通用代理。ContextCompiler 预装所需规划 Skill 和批准事实；搜索、读文件等采集由独立 EXECUTE Activity 完成。adapter 的工具拒绝与 Kernel/Broker 的身份校验必须分别实现，禁止在 PLAN 会话热加载工具或切换执行身份。

## 1. 技术与部署基线

Python/FastAPI/Pydantic负责ControlKernel、HTTP与ReadModel；TypeScript/ESM负责Runner及Harness adapter；React/TypeScript负责Web。PG保存业务权威状态，pgvector只辅助检索，S3兼容对象仓保存内容，Git保存提交，Docker/VM隔离执行，OpenTelemetry/Prometheus/Grafana观测。

逻辑module不等于微服务。Kernel的API/controller两个入口共享同一application implementation及事务规则；Runner协调和Harness adapter合成一个部署单元，避免Python Worker与TS adapter之间重复维护lease状态。不同角色仍在不同activation容器/身份运行。可信ExecutionBroker保持隔离，绝不能为减少进程把宿主凭据放入Runner。

| 部署单元 | 包含 | 身份/网络 |
|---|---|---|
| control-api / control-controller | 同一代码包中的Kernel、Ledger控制逻辑、ContextCompiler、ReadModel；不同进程入口 | 服务DB权限；API不挂长期调度loop；collector不拥有任意业务写权限 |
| runner | TypeScript生命周期协调、fake/Harness adapter、角色context | 无DB/宿主socket/签名key；只调用已授权内部协议 |
| execution-broker | 工具准入、受信执行、collector、凭据与沙箱管理 | 窄范围运行权限；结果交Ledger；不直接改Task表 |
| web | 静态前端，可由反向代理托管 | 仅同源API、无服务凭据 |
| dependencies | PG、对象仓、模型、身份、遥测 | 私有网络与明确scope |

具体依赖版本在W01锁定。上游Node/pnpm/commit事实见[09](09-Harness上游核验.md)，不能从上游构建通过推断本项目运行通过。不另叠Redis锁/第二调度器；未来引入Temporal等必须替换对应职责并迁移状态。

## 3. Interface与所有权

```text
API/Runner → Kernel类型化命令与Activity outcome → domain规则
                         ↓ 短事务
              storage + journal + outbox
Broker → Kernel准入 → 受控执行 → Ledger回执 → Kernel结果结算
ReadModel ← 已确认状态/事件；Web只读投影并提交用户意图
```

五个module保留内部可测试小实现，caller不自己拼接lease→预算→审批→effect多次写库。Kernel是唯一业务转换写入者，Ledger控制不可变证据与引用的合法性；Broker仅通过Kernel准入/结果interface。domain无网络/文件IO，时钟/DB/模型/对象仓通过依赖注入。

Python↔TS固定ActivityLease/Outcome/Evidence schema；fake和Harness adapter穿过相同seam。上游字段变化只修改adapter，不能牵动DAG/预算/最终判定。所有后台长动作登记Activity；无目标的探测/验证/索引使用项目运维budget scope。

## 4. PG约束与版本

| 表组 | 必要约束与索引 |
|---|---|
| goals/contracts/plans/tasks/coverage/profiles | (goal_id,contract_revision)/(goal_id,plan_revision)唯一；覆盖两端同Goal，coverage.profile匹配Task验收profile；Goal最终profile独立校验；profile不可变 |
| activities | (budget_scope_id,status,wake_at,id)调度索引；goal_id/task_id可按kind为空；kind/target匹配 |
| activity_attempts | UNIQUE(activity_id,fencing_epoch)，每Activity一ACTIVE部分唯一；lease_expires_at索引 |
| steps/effects | UNIQUE(activity_id,logical_step_id,intent_revision)，同step只有一个effect；根/前驱唯一后继；V1 intent_revision=1；payload绑定不可改 |
| effect_receipts | UNIQUE(effect_id,receipt_id)，冲突内容隔离；迟到inbox不直接写活动结果 |
| approvals/consumptions | scope+subject(type/id)+payload+policy绑定；UNIQUE(approval_id)；消费与DISPATCHED同事务，过期/撤销不准dispatch |
| budget/resource ledgers | reservation_id唯一；结算幂等；失租不自动释放物理资源或未知费用 |
| barriers/manifests/audits | 每Goal最多一有效屏障；封存内容不可更新；审计生产者与subject分离 |
| evidence/artifacts/checkpoints | 所有引用存在、同项目、内容摘要匹配；有效引用阻止GC |
| events/outbox | (goal_id,seq)及event_id唯一；状态与事件同事务 |

业务state_revision、合同/计划版本与fencing_epoch分开；renewal_seq只影响lease，不推进业务版本。数据库用UTC时间决定lease到期，不能信Runner本地时钟。金额decimal，epoch BIGINT存储、JSON字符串传输。

锁按scope→Activity（需要时）→step/effect→approval→资源→预算排序，事务超时/死锁重试均有限且不跨外部IO。屏障关闭与工程dispatch持同scope锁，DISPATCHED计数覆盖网络发出前后的未知窗口。PG行锁不是跨服务外部效果事务。[PG锁说明](https://www.postgresql.org/docs/current/explicit-locking.html)

VerificationProfile与工具registry固定digest；replay_class/scope不由模型决定。内部导出信任受protected DB/身份认证保证；离线包需要DSSE JSON Envelope 1.0.2 provider的signature/key_id/trust bundle及预配置根信任，并测试轮换、撤销和未知key拒绝，不自造签名算法。

## 6. 启动、暂停与关闭

开发/测试Compose用独立project，production保留同样可信边界。macOS容器访问模型不能假设127.0.0.1指向宿主；配置明确代理地址及身份，只开放所需网络。

顺序：PG/对象仓/测试身份源→单实例migration→受控seed→API/controller/Broker/Runner→Web。readiness检查schema与必要依赖；模型失败可只读降级但不派发模型活动，PG失败不能把任务列表当空。

API生命周期仅管理连接/资源，不在每个Web worker启动一个scheduler；采用FastAPI lifespan管理启动/关闭资源。[官方说明](https://fastapi.tiangolo.com/advanced/events/)

drain：停止新claim/工程dispatch→发checkpoint/stop→收可信receipt→核对未决effect和资源→关闭attempt/释放已证明释放的资源→退出。异常退出后恢复扫描接管全部ActivityKind；租约结束不能证明远端命令未发生。暂停后只允许必要只读对账/收尾；最终屏障下的验证不具有工程写权限。

## 9. 备份、恢复与发布

PG基础备份+WAL，工件版本/不可覆盖策略，Git bare mirror/bundle；备份manifest关联DB恢复点、对象/Git集合、schema、合同/策略/验证配置版本及公开信任包。签名密钥单独受控备份，不随证据包分发。

进程/宿主重启且持久存储完整时已确认事务RPO=0；存储灾难初始目标RPO≤5min、RTO≤60min，必须T21实测。恢复到新环境：隔离旧执行者/凭据→恢复DB/对象/Git→校验引用和公开信任包→缺材料标BLOCKED→重新签worker身份并提升恢复代次→重建读视图→对账所有DISPATCHED/UNKNOWN→只读就绪→核验后开准入。恢复绝不能自动把SEALED屏障改成允许写入。

迁移expand/migrate/contract，应用回退不等于外部效果回滚；破坏性迁移先有可验证备份。发布绑定应用commit、上游SHA、镜像、迁移和最终ReleaseManifest。完整交付包括脚本/配置/CI/仪表盘/文档；命令只有真实脚本落地并验证后才能标可运行。

## 11. MEA隔离实现归属

context_compiler负责角色allowlist、记忆来源/版本、压缩快照；runner adapter负责新轮/新审计session与受控同轮恢复；evidence_ledger负责ProtectedBaseline/检查记录；execution_broker负责不可写挂载、沙箱临时空间、缓存隔离和可信采集。Kernel负责依其结果拒绝完成与持久化状态，模型只提交提案。

Golden/holdout/验证器不放入Executor可写checkout或共享可写缓存。读取候选运行构建时禁止宿主socket/服务凭据，网络默认拒绝；批准网络访问仍须合同与registry许可。审计工作区及模型上下文缓存按角色/版本隔离，不复用Executor会话缓存。受信Runner宿主的模型推理也要预留/结算预算和检查数据范围，零工具不意味着模型调用免费或可任意出网。


## 12. MEA持久化补全

| 对象/表 | 所有者 | 必要约束 |
|---|---|---|
| context_bundles | ContextCompiler经受信存储入口 | 不可变Content与角色ACL；activity/attempt关联；反馈引用及压缩来源持久 |
| protected_baselines | Ledger | Goal合同版本唯一；隐藏内容隔离；digest不可改 |
| baseline_checks | Ledger/可信collector | 绑定attempt、phase、轮次与候选；必要检查缺失阻止验收 |
| goal_reviews | Kernel接收受信诊断 | 绑定不可变运行快照，不能当候选验收 |
| audit_aggregations | Kernel | 固定必要集合digest与已受理审计集合，不接受模型覆盖 |
| planning_feedback / planning_feedback_consumptions | Kernel | 反馈内容唯一键含nullable Task语义；消费UNIQUE(plan_activity_id,feedback_id)，与PLAN outcome原子提交 |
| session_cleanup_records | Runner宿主/Kernel恢复程序 | UNIQUE(attempt_id,session_generation)，状态可重试，无原始推理；终态/过期扫描补清理 |

这些是01开发文档§11核心表清单的补充，W01必须同时生成迁移并接入冻结Content schema校验，不能只建旧核心表。baseline/check/context文件字节先存对象仓再登记引用；feedback与Audit/outbox在同一业务事务；轨迹不存可备份业务对象仓。原始轨迹TTL配置RING_SESSION_TRAJECTORY_TTL_SECONDS默认1800，限制非负有界；成功终态立即清理，失租/失败/取消不超过截止，重试不滚动延长。清理失败按有界维护策略重试并告警，metadata记录保留而非伪造成功。

claim及outcome仍走统一Kernel，不另开第二调度器。会话清理属于受信固定维护动作，恢复元数据能扫描；其失败不能让旧会话重新获得权限，未确认进程停止仍遵守quarantine。


## 13. v0.5冻结新增存储与所有权

model_invocations由Kernel登记、受信模型连接器发出，UNIQUE(activity_id,invocation_seq)；model_receipts按(invocation_id,receipt_id)去重，迟到不推进旧attempt。approvals持久subject_type/subject_id，类型限定EFFECT/MODEL_INVOCATION，消费UNIQUE(approval_id)且必须绑定原subject。停止表stops保存request_id唯一请求及具体activation，stop_receipts按stop/receipt去重，每个resource_instance_id独立确认。memory_indexes提供MEMORY_INDEX target的持久身份及固定输入摘要。binding_adoptions由Kernel在计划发布事务登记，UNIQUE(binding_digest,new_plan_revision)，只允许合同/依赖输入/策略/候选完全不变的保留节点，proof_digest记录适用性证明。所有新增表遵守项目复合外键、固定锁序和outbox事务规则。

恢复验收由Kernel唯一RECOVER_FINALIZATION命令实现，API和controller共用相同application入口。ExecutionBinding在创建Activity时固定；attempt绑定其摘要，context_digest原子写一次。连接器只读取模型凭据，不取得工程写许可。StopReceipt ISOLATED不释放GPU/CPU；只有证明实际释放才回收。
