# 真实业务 E2E 驱动开发案例：订单幂等修复

> 状态：E2E-0～E2E-5 **业务全路径 + 六注入点恢复红队**已通；官方 Loop **scripted** 多步→DONE 已通（≠模型自主）。**chat-driven** 已通：双工具 live×Gateway、诊断 FSM×Gateway（含 seal）、**live 诊断×Gateway×seal**（可 followup）。订单 **三层 AUDIT × FINALIZE → Goal DONE** 已通。**RunActivation EXECUTE diagnose**：FSM×独立 Broker→Goal DONE；**live 零 USER_PROMPT**（profile 仅从 Goal 合同进工具 schema；objective 装配文案）×独立 Broker→Goal DONE **verified**（`RING_E2E4_LIVE_CHAT=1`）。仍缺：默认打开 live CI、完整 V1/M5/100h。  
> 日期：2026-09-12  
> 定位：以一个可复现的真实开发任务驱动 Ringharness 补齐端到端闭环；本文件是执行提案，不修改 v0.5 冻结规格。  
> 权威约束：领域语义以 `doc/01-开发文档.md`、接口以 `doc/05-API接口文档.md`、验收以 `doc/02-测试文档.md` 与 `doc/03-收敛文档.md` 为准。

## 1. 目标

让用户通过 Ringharness 提交一个真实软件开发 Goal：

> 修复订单服务的幂等缺陷。同一个 `Idempotency-Key` 重复提交订单时，只能创建一个订单并扣减一次库存；补充测试，全部测试通过后提交候选。独立审计必须在只读候选副本中复跑公开测试和隐藏并发测试。只有固定 VerificationProfile 全部通过且无未决 Effect，ControlKernel 才能判定 DONE。

这条场景不是展示脚本。它应作为后续开发的 tracer bullet：从用户 Goal 出发，每次遇到真实缺口就登记失败证据、切出最小修复批次、复跑同一场景，直到完整闭环成立。

### 1.1 DeepSeek Harness 是硬性被测对象

本案例必须通过仓库固定 SHA 的 **DeepSeek Harness 官方 AgentLoop** 完成 Executor 多轮执行。它不是辅助组件，也不能用本仓自建两轮循环、直接调用模型 API 或测试代码手工串接 ToolResult 代替。

Harness 路径的最低证明：

1. 从 `RING_HARNESS_CHECKOUT` 加载实际上游构建产物，并核对 checkout commit 与仓库 pin 一致。
2. `RunActivation EXECUTE` 明确选择 `RING_HARNESS_EXECUTE_RUNTIME=deepseek-official-agent-loop`。
3. 由官方 AgentLoop 创建 session、发送用户消息、产生真实 tool call、接收 ToolResult 并进入后续模型轮次。
4. 至少完成 `read_file → run_tests → write_file → run_tests → seal_candidate` 的多步循环；不能由测试宿主预先写死每一步调用顺序后冒充 AgentLoop 决策。
5. Harness 只负责循环与会话，所有工具调用仍进入 Effect Gateway；Runner 不直接执行工具、不调用 Effect `/dispatch`、不写业务 DONE。
6. 运行摘要记录 Harness pin、driver、session generation、模型轮次、tool call ID 与对应 Effect ID，禁止持久化隐藏推理。

任一证明缺失时，本案例状态只能是 `PENDING_HARNESS` 或失败，不能静默回退到 `default`/`cordis` 路径后报告 E2E 通过。

## 2. 为什么选这个案例

该问题具备真实业务开发的关键特征：

- 需要理解现有代码，而不是生成一个孤立文件。
- 需要运行测试得到失败证据，再修改代码和复测。
- “接口返回 200”不等于业务正确，必须核对订单数和库存变化。
- 重复请求与并发请求能暴露竞态、幂等、恢复和重复副作用问题。
- 可以完全在本地测试，不涉及真实资金、生产数据或外部账号。
- 任务足够小，适合作为第一条 E2E；又足够完整，能驱动工具、证据、审计和 DONE 屏障落地。

### 3.1 固定业务输入

```json
{
  "sku": "SKU-001",
  "quantity": 2,
  "unit_price": "19.90",
  "idempotency_key": "checkout-20260912-001"
}
```

初始库存固定为 `10`。同一个 key 调用两次或并发调用两次后的验收结果：

```text
orders.count == 1
orders[0].quantity == 2
inventory["SKU-001"] == 8
两次响应指向同一 order_id
```

不同 key 的请求仍应正常创建不同订单并分别扣减库存，防止通过“拒绝所有第二次请求”作弊。

## 4. E2E 拓扑与权威

```text
用户 POST Goal / START
        │
        ▼
Temporal GoalWorkflow ── 只负责持久编排与恢复
        │
        ▼
Manager / PLAN ── 工具集必须为空，只提交候选计划
        │
        ▼
ControlKernel ── 校验计划、租约、预算、角色与准入
        │
        ▼
Executor / 官方 DeepSeek Harness AgentLoop
        │  tool proposal
        ▼
Effect Gateway → 独立 ExecutionBroker → 隔离 worktree
        │  receipt + artifact + evidence
        ▼
CandidateManifest 封存
        │
        ▼
Auditor / 独立身份 / 只读候选副本
        │  公开测试 + 隐藏并发测试
        ▼
VerificationAssessment / AuditAggregation
        │
        ▼
ControlKernel FinalizationBarrier ── 唯一 DONE 权威
```

权威边界：

| 事实 | 唯一权威 |
|---|---|
| 多轮思考与工具回灌 | 官方 Harness AgentLoop |
| Activity 生命周期与恢复 | Temporal Workflow |
| 工具是否允许、Effect 状态、业务状态 | ControlKernel / PostgreSQL |
| 工具真实执行 | 独立 ExecutionBroker |
| 字节、回执和工件 | EvidenceLedger / 对象仓 |
| 候选是否满足合同 | 独立 Auditor + 固定 VerificationProfile |
| Task / Goal DONE | ControlKernel 最终屏障 |

## 6. 分阶段实施

每阶段只解决当前最先出现的真实阻塞。前一阶段没有稳定通过，不进入后一阶段。

### E2E-0：可重复目标仓库

实现目标：一条命令生成带已知缺陷、固定 commit 和独立 worktree 的订单服务仓库。

建议新增：

- `tests/fixtures/business_e2e/order_service/**`
- `scripts/seed_business_e2e.py`
- `tests/e2e/test_business_fixture.py`

完成条件：

1. 初始公开幂等测试稳定失败。
2. 参考修复应用后公开测试与隐藏并发测试稳定通过。
3. 连续初始化两次得到相同初始 commit 和相同输入摘要。
4. 清理只删除指定 `run_id`，保留失败证据，不操作其他工作区。

### E2E-1：真实只读诊断链

实现目标：真实 Goal 启动后，官方 AgentLoop 通过独立 Broker 读取目标仓库文件，ToolResult 回到模型第二轮。

完成条件：

1. `POST /goals/{goal_id}/start` 经 Temporal 启动，不走 LEGACY claim。
2. PLAN activation 暴露工具数为 0，Step/Effect 新增数为 0。
3. EXECUTE 使用官方 AgentLoop，driver 为 `deepseek-official-agent-loop`。
4. `read_file` 经独立 Broker 进程执行，形成 `PREPARED → DISPATCHED → SUCCEEDED`。
5. ToolResult 内容在第二轮模型输入中可证明存在。
6. Goal 仍不是 DONE。

### E2E-2：最小受控开发工具集

实现目标：只增加该案例必需的受控工具，不开放任意宿主 shell。

建议工具能力：

| 工具 | 允许范围 | 必需证据 |
|---|---|---|
| `read_file` | Executor worktree 内相对路径 | 输入路径、内容摘要、截断信息 |
| `write_file` | Executor worktree 内批准路径 | 修改前后摘要、patch artifact |
| `run_tests` | 固定 argv 模板，例如订单服务的 pytest | argv、cwd、stdout/stderr artifact、exit code、timeout |
| `git_diff` | 只读 diff/status | base commit、diff artifact、工作树状态 |
| `seal_candidate` | 固定 worktree 与当前 attempt | commit、CandidateManifest、依赖锁摘要 |

`run_tests` 应使用验证器 registry 中批准的命令模板。第一条 E2E 不提供 `shell(command: string)`，避免把权限模型绕成任意命令执行器。

完成条件：

1. Executor 能观察红测、修改实现、复跑到绿、输出候选。
2. 路径穿越、绝对路径、符号链接逃逸和越 workspace 写入均失败关闭。
3. 相同逻辑工具动作在重试后复用原 `effect_id`，不重复执行写入。
4. 工具 exit 0 只完成 Effect/Activity，不修改 Task/Goal DONE。
5. 候选封存后 Executor 工程写入准入关闭。

### E2E-3：独立审计与业务验收

实现目标：Auditor 在独立只读候选副本中验证业务结果，不能复用 Executor 自报。

固定 VerificationProfile 至少包含：

- MECHANICAL：依赖安装、公开测试、格式/类型检查。✅（公开 pytest + 层门禁）
- SEMANTIC：顺序重复与并发重复均只产生一个订单、只扣一次库存。✅（层 AUDIT + 夹具 score 阈值；隐藏并发测在物化树上绿）
- ADVERSARIAL：不同 key 仍能创建不同订单；旧 key 不返回其他用户订单；隐藏测试未泄露给 Executor。✅（层 AUDIT；Executor 无 `tests_hidden`）

完成条件：

1. Auditor 与 Executor 的 worker identity、attempt、workspace 均不同。
2. Auditor 只能读取封存候选和批准验证器，不能修改候选。
3. 每个必要 criterion 有恰好一条当前候选、当前 profile、当前 round 的有效 Assessment。
4. 删除测试、空断言、硬编码固定 key 或伪造 stdout 都得到 FAIL 或 INSUFFICIENT。
5. Auditor Activity SUCCEEDED 且 verdict=FAIL 时，Task/Goal 仍不 DONE。

### E2E-4：Kernel 最终完成闭环

实现目标：将候选、独立审计和最终屏障连成真实业务完成链。

完成条件：

1. Task 必要验证全部 PASS 后才转 DONE。
2. Goal 的必要任务、集成候选、GLOBAL 验证、Evidence、预算与 Effect 全部结算。
3. FinalizationBarrier 关闭工程准入并完成排空。
4. ReleaseManifest 与最终候选、合同、计划、profile digest 一致。
5. 只有 ControlKernel 最终事务写 Goal DONE；代码中不存在 Runner/Harness/Auditor 直接 DONE 路径。
6. `GET /goals/{id}/release` 能返回固定发布清单及有效性状态。

### E2E-5：恢复与重复副作用红队

实现目标：对同一业务 Goal 注入真实崩溃，验证恢复不会重复扣“库存”或重复执行工具写入。

至少覆盖：

| 注入点 | 预期结果 |
|---|---|
| Effect PREPARED 后杀 Runner | ✅ 新 attempt 复用原 `effect_id`，不新建重复 Effect（`test_e2e5_prepare_crash_order_write`，×10） |
| Broker 已写文件、回执提交前退出 | ✅ Effect→UNKNOWN；迟到回执 `PENDING_RECONCILIATION`；对账前不重试/不 DONE（`test_e2e5_write_receipt_crash_unknown`，×10） |
| 测试执行完成、Evidence 写入前退出 | ✅ 不伪造 SUCCEEDED；本地可重跑只读 pytest；写盲重试关闭（`test_e2e5_run_tests_evidence_crash`，×10） |
| CandidateManifest 封存后杀 Executor | ✅ 密封 digest 不变；Auditor 物化可续；Executor 重领 `STEP_CONFLICT`（`test_e2e5_seal_kill_executor`，×10） |
| Audit run 登记后、Audit 提交前退出 | ✅ VerificationRun 后失租；×10 伪造 PASS/FAIL outcome 失败；Task/Goal ≠ DONE（`test_e2e5_audit_mid_crash`） |
| Finalization CAS 前断线 | ✅ 重试后恰好 1 个 ReleaseManifest；Goal DONE 后无终态复活（`test_e2e5_finalization_cas_crash`，×10） |

完成条件：每个注入点至少重复 10 次，外部执行计数、Effect 数、receipt 数、库存结果与最终状态均满足不变量；任何一次出现重复写入或 False DONE，场景保持红色。

## 8. 核心断言

### 8.1 业务断言

- 同 key 顺序请求两次：一个订单、扣一次库存、相同 `order_id`。
- 同 key 并发请求两次：一个订单、扣一次库存、相同 `order_id`。
- 不同 key：两个订单、库存分别扣减。
- 修复没有删除或弱化测试。

### 8.2 平台断言

- PLAN 工具调用、Step、Effect 均为 0。
- Harness checkout commit 与 `apps/runner/src/harness/pin.ts` 当前固定 pin 一致。
- EXECUTE driver 明确为 `deepseek-official-agent-loop`，没有走本仓自建 AB01 两轮循环。
- 官方 AgentLoop 至少发生两轮模型调用，并在后续轮次读到真实 ToolResult。
- 所有 Executor 工具动作均有 Step、Effect、receipt 和 evidence。
- Runner 没有调用 Effect `/dispatch`；独立 Broker 是唯一执行者。
- ToolResult 确实进入官方 AgentLoop 后续轮次。
- Executor、Auditor 身份与 workspace 隔离。
- 候选 digest 与 Auditor 读取的 digest 一致。
- UNKNOWN、缺证据、未确认 Stop、Trust BLOCKED 任一存在时均不能 DONE。
- 模型文本出现“完成”、工具 exit 0、Activity SUCCEEDED 均不能直接导致 DONE。
- 成功路径恰有一个 ReleaseManifest；失败路径为 0。

## 9. 失败驱动的迭代规则

每次 E2E 失败只归入一个首要分类：

| 分类 | 示例 | 下一步 |
|---|---|---|
| `ENVIRONMENT` | Harness 未 build、Temporal/模型不可达 | 修启动契约或失败关闭；不得改断言绕过 |
| `CONTRACT` | API 字段、digest、状态机不一致 | 同批更新 schema/迁移/客户端/测试 |
| `ORCHESTRATION` | Activity 未 admit、恢复卡死 | Hermes 路径 Issue；Cursor 不越界改 orchestration |
| `HARNESS` | 没有工具调用、ToolResult 未回灌 | 修 adapter/上下文/循环接线 |
| `BROKER` | Effect 不 dispatch、回执缺失、越界 | 修独立执行与身份/租约校验 |
| `EVIDENCE` | 结果存在但 artifact/digest 不完整 | 修可信采集，不把日志文本当 PASS |
| `VERIFICATION` | 隐藏测试没跑、错候选或错 profile | 修独立审计与 Assessment 绑定 |
| `FINALIZATION` | 缺项仍 DONE 或全 PASS 仍卡住 | 红队阻断，修 Kernel 屏障 |
| `PRODUCT` | 用户无法理解 BLOCKED/UNKNOWN | 后续补 UI 和可操作诊断 |

处理循环：

```text
运行同一 Goal
→ 保存首个失败的结构化证据
→ 建立一个最小批次/Issue
→ 只修该 seam
→ 跑定向测试
→ 从干净 run_id 重跑完整 E2E
→ Codex 独立复跑
```

不得为了让场景变绿而降低 Goal 合同、删隐藏测试、把真实进程替换成内部 mock、扩大工具权限或手工修改数据库状态。

Harness 专项失败必须进一步区分：

- `HARNESS_PIN_MISMATCH`：checkout 与固定 SHA 不同，启动前失败关闭。
- `HARNESS_AGENT_LOOP_NOT_BUILT`：上游 peers 未构建，保持 pending，不回退其他循环。
- `HARNESS_OFFICIAL_DRIVER_MISSING`：没有证据证明官方 AgentLoop 实际创建并驱动 session。
- `HARNESS_TOOL_RESULT_NOT_REENTERED`：工具已执行，但结果没有进入后续模型轮次。
- `HARNESS_GATEWAY_BYPASS`：Runner/Harness 绕过 Effect Gateway 或自行 dispatch，整次 E2E 直接失败。
- `HARNESS_SESSION_RESUME_INVALID`：崩溃后恢复了错误 generation、重复工具副作用或丢失原 Effect 关联。

## 10. 证据目录与报告

每次运行输出：

```text

├── run-summary.json
├── goal-snapshot.json
├── temporal-history.json
├── effects.json
├── receipts.json
├── candidate-manifest.json
├── audits.json

├── executor-test-output.txt
├── auditor-public-tests.txt
├── auditor-hidden-tests.txt

```

`run-summary.json` 至少记录：代码 commit、Harness pin、模型/provider、开始/结束时间、Goal/Activity/Effect ID、各阶段 observed/verified/accepted/completed/done 状态、失败分类与证据相对路径。不得记录 token、密钥、隐藏测试正文或模型隐藏推理。

## 11. 门禁与交付节奏

建议节奏：

1. **当天**完成 E2E-0 与 E2E-1，得到真实官方 AgentLoop + 独立 Broker 的只读闭环。
2. **随后 1–2 天**完成 E2E-2，使 Agent 能真正修改并测试目标仓库。
3. **随后 1–2 天**完成 E2E-3/E2E-4，形成独立审计与 Kernel DONE。
4. E2E-5 单独作为恢复红队批次；稳定后再扩大真实仓库复杂度和运行时长。

每批必须同时提交：

- 本批定向红绿测试；
- `pnpm test` 与 `pnpm run build`；
- 必要的 Python 定向测试；
- CI 链接；
- 精确 evidence 路径；
- 明确的 non-goals 与 residual risk。

正式结论以 CI 和 Codex 独立复跑为准。本机共用数据库或 Temporal 造成的失败，必须与 `origin/main` 同用例结果对照，不用单次本地全量结果直接判退。

## 12. 本案例何时算完成

全部满足才关闭案例：

1. fake chat 与真实 Qwen/DeepSeek 各完成至少一次同栈 E2E。
2. 两次均由固定 SHA 的 DeepSeek Harness 官方 AgentLoop 驱动多轮工具循环，没有 fallback。
3. 真实独立 Broker 执行全部工具，Runner 没有旁路 dispatch 或本地执行。
4. 订单幂等的公开、隐藏、并发和反作弊断言全部通过。
5. Executor 与 Auditor 身份、上下文、workspace 和验证器隔离有持久证据。
6. crash matrix 无重复副作用、无丢失 UNKNOWN、无 False DONE。
7. 失败场景可从 `run_id` 一次性定位 Goal、Activity、Effect、Evidence、Audit 和 Barrier。
8. ControlKernel 生成唯一 ReleaseManifest 并判定 Goal DONE。
9. Codex 独立验收通过，Hermes 未触发红线否决，CI 全绿。

100 小时无人值守不是本案例的完成条件；本案例稳定后，才能把它作为 100h 运行中的重复业务 Goal 模板。
