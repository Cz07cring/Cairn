## 3. 立即生效的流程门（本文件的实质产出）

前五道是**机械门**（可在 CI 或 PR 模板强制），后两道是**习惯门**（靠认领与验收执行）。

### 门 1：批次模式卡片（Cursor 已登记，Hermes 采纳）

认领时须写满 `problem` / `pattern` / `owned_loop` / `side_effect_throat` / `done_authority` / `seam` / `contrast` 七字段。

### 门 2：Temporal 演变门（P0，Codex）

任何改动 `packages/orchestration/**` 的批次，提交必须包含：

1. **patch ID**（或明确声明「本批不改确定性命令序列」）；
2. **旧历史 + 新历史双 replay fixture 各一**，且断言：旧历史**不得**调用新 Activity，新历史**必须**调用；
3. **CAN 携带字段清单**（`command watermark` / `owner_epoch` / `running attempt` / `action identity` 等），并断言连续两次 CAN 后这些字段不丢；
4. **非确定性扫描**：Workflow 模块不得直接网络 / DB / 环境变量 / 非确定性时间随机（静态检查可入 CI）。

> 判据来源：B 报告 Top 1。理由：已有两个 patch 证明做法可行，但**个人纪律要升级为机械门**——否则「旧历史重放」迟早被漏掉。

### 门 3：恢复安全门（P0，Cursor）

Continue-As-New / 崩溃恢复路径上，恢复**不得**自动获得幂等；无人值守恢复最危险的失败是**恢复执行了一个已过期的破坏性意图**。因此恢复侧须带：

1. `intent_valid_until`（过期窗口）；
2. `checkpoint_schema_version`（版本不兼容即拒绝）；
3. `recovery_attempts` 计数与上限；
4. 显式**恢复开关**（默认关闭者须说明）。

**两条已核原文的精确要求**（第 40 章，2026-09-12 实读）：

- **尝试计数必须在模型调用之前落盘**，否则崩溃循环会把它永远清零 —— 计数写入与「即将执行危险动作」之间不得有未持久化的窗口。
- **Checkpoint 打在阶段边界并做防抖**（约 2 秒级），不是每轮迭代、也不是只在最后；压缩摘要写完是最该打的边界之一（那份摘要很贵，丢了要重买）。

**参考默认值**：书中公开实现的过期窗口默认 **4 小时**，理由写在配置里（「覆盖同一工作会话内的崩溃/升级重启；更旧者等于执行一个无人监督的陈旧用户意图」）。本仓不照搬常数——见 §7 待裁定 2。

验收：time-skipping / replay 覆盖「过期」「版本不兼容」「调用前后崩溃」「取消后重启」四类；断言旧意图进入 REVIEW/ABANDONED、`DISPATCHED`/`UNKNOWN` **只走对账**、dispatch 总数不增加、Goal 非 DONE。

> 判据来源：A 报告 Top 3（第 40 章）。**恢复的 Turn 永远算无人值守**，不论它原来从哪来。

**与既有红线的衔接**：第 40 章明确指出「恢复一个 Turn 不等于让它幂等——Checkpoint 只记录工具**被调用过**，记不了副作用有没有落地；防线在工具层，不在恢复层」。这正与本仓既有设计一致：防线是 `effect_id` 幂等 + UNKNOWN 先对账，**不是**恢复机制本身。因此本门只加「窗口/版本/计数/开关」，**不得**借恢复机制去补幂等。

### 门 4：验收五问（Cursor 四问 + Hermes 增补）

在前四问基础上增补第五问：

1. 循环归谁？（只允许 Harness / Runner activation；本仓自建 Loop → 退回）
2. 副作用咽喉在哪？（只有 Gateway/Broker 路径产生 effect？有无本地捷径？）
3. 失败怎么停？（UNKNOWN / 关闸 / Stop CONFIRMED / 版本门）
4. DONE 有没有被碰到？（断言 Goal≠DONE，或明确「未触达」）
5. **【新增】恢复与幂等是否成立？** 崩溃/失租/重放后，是否为同一 `effect_id`、是否先对账、dispatch 次数是否未增加？

### 门 5：契约漂移门（已有 CI 门，补流程）

今日已连续两次因漏跑生成器红灯（辅助批 A 的 manifest 过期、第八十五续改 `probe.py`）。**触及 API/模型的一方在提交前必须**跑 `scripts/generate_contracts.py` 并确认 `git diff -- contracts packages/api-client/src/generated.ts` 为空。

### 门 6：本地必须跑类型检查，不能只跑 vitest（习惯门）

今日两次 main 红的真根因都是 **vitest 通过但 `tsc` 失败**（`stopSeam` 空元组、第九十七批 `args: string | undefined` + `vi.fn()` 无参）。

- vitest **不做类型检查**，`pnpm run build`（`tsc -p`）才暴露；
- 因此批次自证的命令里，**`pnpm run build` 与 `pnpm test` 必须同时出现**；只贴 vitest 输出视为证据不全。

### 门 7：禁止「假进度」形态（Cursor 已列，补两条）

已有：Control 发 tools 冒充 Harness Loop、模型成功/`exit 0`/Activity SUCCEEDED/Workflow COMPLETED 当 DONE、轮询超时本地写 SUCCEEDED、失租盲再 dispatch、为绿测缩减 VerificationProfile。

**新增**：
- 空 tool-call 回合用 `ACTIVATION_SUBMITTED + 空 effect_ids` 冒充推进（第 96 批已修，列入永久禁止）；
- 用「批量大结果静默截断」换取上下文不超限（属销毁信息，应外溢到 Artifact 并保留取回路径）。

闸门不变：**Temporal 接入与恢复 > 新业务面**；未通过当前阶段安全边界，不开启下一阶段。

```text
M3 收口（现在）   门1 门3(#1 恢复安全门) 门2(#2 Temporal 演变门) 门6 门5
   ↓
M3.5              #4 Tool Result Envelope → #5 Watchdog → #8 No-Progress Guard
   ↓
M4 前             #6 PlanStaticValidator → #7 HandoffEnvelope → #9 预算闭环
                  #10 ToolCapabilityManifest → #11 负向矩阵
   ↓
M5 发布门         #12 安全并行 → #13 可观测 SLO → #14 策略影子评估 → #15 provenance 账本
```

**为什么把并行放最后**：A 报告明确指出并行会同时放大上下文体积、超时与对账复杂度（第 44 章「并发安全属于具体调用而非工具名」）。必须先把调用身份链（`tool_call_id → step_id → effect_id → receipt_id`）与结果预算打通，再开保守并行。

**不抢跑**：第 38–39 章（Deferred Tool Loading / Prompt Cache 稳定性）与第 45 章（Computer Use 上下文管理）属成本与新工具面专项，**在安全闭环完成前不作为独立批次**——但它们的具体机制已记入 A 报告，M4 时按需取用。

## 5. 与书中做法的显式折中（重要）

本书是通用最佳实践，与 ringharness 红线有**三处必须明确的冲突**。不是「书中错了」，而是本项目更严：

| 书中通用建议 | 本仓折中 | 理由 |
|---|---|---|
| 策略引擎 fail-open（策略缺失/编译失败时放行，保可用性） | **一律 fail-closed 或 503** | `doc/01`：缺 JWT/库/密钥/仓库别名时 503，禁开发万能身份。可用性不得换来授权绕过 |
| 为三层架构引入 Go/Rust、OPA、WASI 沙箱 | **不换业务语言**；沙箱以 spike 实测选型（rootless container 或 WASI），不预设 | v0.6 §1.1 已裁定 Python 控制面 + TS Runner；吸收的是**职责分离模式**，不是技术清单 |
| 沙箱执行成功 / Workflow COMPLETED 作为完成信号 | **都不提升为验收正确性或 DONE** | 完成只走 Kernel + 固定 VerificationProfile + 屏障 |

另需保留的一条判据：**恢复不自动提供幂等**。书中「崩了就从断点接着跑」是效率诉求；本仓对**不可安全重试的未知操作**要求进入可解释阻塞，而非续跑。

## 6. 不做什么（防抢跑清单）

- 不在 Control / `runActivation` 内自建完整多轮 Agent Loop（循环归 Harness）。
- 不为「能连上模型」加假调度或绕过 Kernel/Broker 的捷径。
- 不把 `plan_terminal_statuses` 里出现 SUCCEEDED 当作任务成功。
- 不为通过绿测而放宽 `TokenBudget`（超限应拒绝并让上游裁剪，不得静默截断）。
- 不在 M3 安全边界全绿前开 M4 产品化表面（UI/Verifier 产品化）。
- 不把本文件的建议当作已实现——一切以代码与 `contracts/implementation-coverage.json` 为准。
