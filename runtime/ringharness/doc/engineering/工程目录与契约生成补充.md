# 工程目录与契约生成补充

> 基于完整 V1 v0.5，工程补充修订 E01。仅细化目录布局、契约生成与 W01 验收，不改变业务协议、角色权限或验收标准。应用文件和下述生成脚本均待实现；本补充不是应用完成证明。

配套原文：[08 工程化结构](../08-工程化结构文档.md)、[05 API 合同](../05-API接口文档.md)、[06 E2E](../06-E2E开发调试文档.md)。原 v0.5 冻结包保留不变。实施时原 08 §2 的合并路径以本补充展开路径为准；业务约束继续遵守 01/05 及冻结 Content Schema。若发现业务语义冲突，应升级规格，不通过生成器暗改。

## 1. 契约来源、版本与生成方向

| 工件 | 权威输入 | 生成或同步目标 | 责任 |
|---|---|---|---|
| Content v3 | doc/contracts/content-v3.schema.json | contracts/content-v3.schema.json，逐字节复制并校验 SHA256 | Ledger 合同维护者 |
| Event v1 | doc/contracts/event-v1.schema.json | contracts/event-v1.schema.json，逐字节复制并校验 SHA256 | Kernel 合同维护者 |
| 摘要规范与向量 | doc/contracts/canonicalization-v3.json、hash-vectors-v3.json | contracts 下同名文件，逐字节复制 | Ledger；Python/TS 共同验证 |
| HTTP 请求与响应 | 05 的字段/路由/错误约定，经 W01 实现为 control_api.schemas 与路由声明 | contracts/openapi.json | Control API；路由与字段逐项对照 05 |
| 内部生命周期协议 | 05 的 ActivityLease/Outcome 等协议，经 W01 实现为 control_kernel.protocols | contracts/runtime-v1.schema.json | Kernel；API 复用这些模型，不重新定义 |
| Web 客户端 | contracts/openapi.json | packages/api-client/src/generated/ | Web；只生成，不手改 |
| Runner 协议类型 | contracts/runtime-v1.schema.json | apps/runner/src/generated/ | Runner；运行时仍必须校验输入 |

原目录中的 evidence-v1.schema.json 是未落地的占位名称，取消该目标，统一使用 content-v3.schema.json；不保留同义别名。runtime-v1 是内部生命周期协议的独立版本域，event-v1 是事件版本域，均不代表 Content v1。历史 Content v1/v2 只读核验，不能生成新证据。

生成方向固定为：冻结规范 → 对应权威 Schema 或经审查的应用模型 → 生成工件 → 消费者。不得从 TS 客户端反向生成 Python 模型，也不得让 OpenAPI 覆盖冻结 Content Schema。Pydantic 对 Content 的适配层必须接受相同合法向量、拒绝相同非法向量，并执行领域校验；通过 JSON Schema 不等于业务验收通过。

W01 落地 scripts/generate_contracts.py：同步固定 Schema，导出 OpenAPI/运行时 Schema，再调用锁定版本生成器生成 TS 客户端/类型。生成过程不访问生产系统、不连接数据库、不启动调度器；配置生成模式使用独立应用工厂。OpenAPI 的服务地址等部署数据不得导致环境间漂移。

生成文件提交版本库并标注生成来源；contracts/generation-manifest.json 记录来源摘要、生成器版本及产物摘要。该清单不把自身列入摘要集合，避免循环。连续两次生成结果必须相同；CI 在干净临时目录生成并逐字节比较，缺失、多余、差异均失败。

## 3. 依赖边界与保护目录

- apps 负责装配，packages 不导入 apps；domain 无网络、文件、模型或数据库 IO。
- Kernel application 通过端口访问 Ledger/ContextCompiler，control 入口注入实现；Ledger/ContextCompiler 不反向依赖 Kernel application。业务转换及跨对象原子提交仍由 Kernel 的统一事务入口控制。
- Broker 服务通过授权协议访问 Kernel/Ledger，不导入 control_kernel.storage，不持有业务数据库写凭据。
- Runner/Web 不导入 Python 实现，不访问数据库；生成协议类型不赋予运行权限。
- verifier 定义位于受信包；真正执行候选代码由隔离执行边界承接，不能直接在控制服务进程运行候选。Auditor 会话由 Runner 以独立角色启动，Kernel 汇总结果。
- tests/fixtures/protected 目录名不是安全机制。真实 holdout/答案不进入 Executor checkout、构建上下文、共享缓存或分发镜像；CI 按角色只读注入独立保护存储。公开 fixture 与保密验收材料分离。

## 4. W01 骨架准入检查

| 编号 | 必须提交的证据 | 失败条件 |
|---|---|---|
| ES01 | Python 包与 pnpm workspace 清单、干净环境安装/import 记录 | 隐式依赖、缺失成员或依赖本机路径 |
| ES02 | 同步 Schema 的摘要对比、两次生成对比、生成清单 | Content/event 漂移、旧 evidence-v1 别名、环境导致不确定输出 |
| ES03 | 05 所有公共/内部路由、字段、错误与模型对应表 | 漏端点、字段不一致；不允许用空 OpenAPI 通过 |
| ES04 | Python/TS 合法与非法固定向量结果 | 任一语言接受非法向量或摘要不一致 |
| ES05 | 包依赖检查与隔离检查 | packages 反向导入 apps、Broker 直连业务 DB、Runner 获得宿主凭据 |
| ES06 | 空库迁移、两入口共享事务路径检查、Compose 配置校验 | API 自启重复调度器、迁移缺约束或角色挂载不隔离 |

ES01—ES06 是 W01 对应工程结构检查，不能替代 W02—W07 的业务、E2E、混沌和 100 小时验收。当前均为待实现验收项，未声称通过。
