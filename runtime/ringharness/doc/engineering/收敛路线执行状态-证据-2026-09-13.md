## 2. 已实测结论

### 2.1 主路径的两个失败机制必须分开看（**已更正**）

**首次 10 轮独立库跑出 10/10**，据此我曾判断「先前失败全是共享库干扰」。
**随后的 20 轮独立库实测否决了这个过度概括**：

| 实验 | 环境 | 轮次 | 通过 | 失败 |
|---|---|---|---|---|
| A | 共享 `ring_test` | 10 | 8 | 2 |
| B | 独立库 | 10 | **10** | **0** |
| C | **独立库** | **20** | **18** | **2（10%）** |

实验 B 的 10/10 是**运气**（样本太小的假象）；实验 C 在**同样的干净条件**下仍失败 2 次。
⇒ 存在**两个互不相同**的失败机制，必须分开归因：

#### 机制 ①：心跳被拒 — **环境性**（独立库 20 轮**零复现**）

共享库那次：`LEASE_HEARTBEAT_FAILED: HTTP 409 attempt 已非 ACTIVE`。
20 轮独立库中**一次都没出现**，且 `EXPIRED=0`（租约从未过期）⇒ 归因共享库互相干扰。

#### 机制 ②：覆盖缺口（模型未收口）— **真实缺陷，干净库照样发生**

实验 C 的 run-009 与 run-019：

| 轮 | modelRounds | 工具调用 | 其中 read_file | executeErrors | missing |
|---|---|---|---|---|---|
| run-009 | 51 | 50 | **44（88%）** | `(none)` | `seal_candidate` |
| run-019 | 23 | 62 | **59（95%）** | `(none)` | `write_file, seal_candidate` |

两轮都报 `OFFICIAL_LOOP_CHAT_DIAG_COVER` 失败，且 `executeErrors=(none)`
⇒ **无进展守卫全程未介入**（详见 Issue #68）。这是「模型原地反复读文件、从不收口」，
与「硬停/软停」无关，也不是环境干扰。

20 轮后的库内终态（独立库，可归因）：`Goal: DONE=18 / RUNNING=2`；
`attempt: COMPLETED=92 / CANCELLED=2`；`EXPIRED=0`；Auditor 拦截 `0/36`。

⇒ 当前**干净环境下真实失败率约 10%**（2/20），机制是覆盖缺口。此前把这一族
也说成「环境干扰」是**错的**，此处更正。

### 2.2 共享库上测出的失败率**不可归因**

根因：全仓（`serve_local` / `test_local` / `check_batch`）共用同一个 `ring_test`；
且 e2e 用例自带跨界批量取消：

```sql
-- tests/e2e/test_e2e4_official_loop_to_goal_done.py:465
UPDATE activities SET status='CANCELLED', updated_at=clock_timestamp()
WHERE status='READY' AND kind='EXECUTE' AND goal_id<>:goal
```

多方共用同一库时**互相破坏**（共享库当时累计 21468 条 attempt）。
⇒ 这正是 AGENTS §7.1 规则 16「本地全量不可信」在 soak 场景下的具体量级：**约 20% 假失败**。
`--isolated-db` 是**必需**，不是可选。

### 2.3 四项指标的可行性与缺口

| 指标 | 状态 | 证据 |
|---|---|---|
| 【3】Auditor 拦截率 | **可用** | 独立库 **20 轮：`0/36 = 0.0%`**（GLOBAL 0/18、MECHANICAL 0/18）|
| 【4】UNKNOWN 恢复率 | 可用（无样本）| 未落终态 0（UNKNOWN/DISPATCHED/PREPARED 全 0）|
| 【1】模型一次成功率 | **结构性不可用** | 见下 |
| 【2】重试成功率 | **结构性不可用** | 同源 |

**【1】【2】为何不可用**：`model_invocations` **只**由 Cordis/Kernel-bridge 路径写入。

- 实测：独立库 **20 个 Goal 全部跑完**（含真实模型调用），`model_invocations` **仍为 0**。
- 静态：`createInvocation` 唯一调用点 = `apps/runner/src/harness/cordisLlmBridge.ts:165`；
  官方 Harness Loop（`openaiCompatibleToolChat.ts` → `executeOfficialRuntime.ts`）**不触及**该端口，
  其头注自述「循环归属 Harness，**不经 Control ModelInvocation.dispatch**」。
- 实测：独立库只跑官方 Loop（模型 deepseek-flash 正常返回）⇒ `model_invocations = 0`，
  而 `goals=1 activities=2 activity_attempts=2`。

而按 AGENTS §7.1 规则 9，**官方 Harness Loop 才是真实无人值守的主路径**。
⇒ 主路径上这两项**分母恒为 0**，是**结构性**结果，不是「样本不足」。

已采取的防御（`report_business_metrics.py`）：把**覆盖范围**直接印在指标下方，
并在「窗口内有 Goal 但 model_invocations=0」时显式提示结构性缺口 ——
防止读者把 `n/a` 当「再跑跑就有」，或把共享库里**别的路径**的数字（曾观测到 `80/344 = 23.3%`）当成功率。

**待裁定（三选一）**：① 官方 Loop 调用回传记账；② 改从 Harness 侧证据计这两项；
③ 契约声明两项仅覆盖 Cordis 路径并为主路径另设指标。

### 硬停真因（2026-09-13 探针实证）：模型发出**空参数的 write_file**

那 3 次 `validation_loop` 硬停，根因由一次性探针（丢弃型 worktree、未提交）取出：

```
[PROBE7] PATH_A_REJECT tool=write_file
         msg="EXECUTE_TOOL_ARGUMENTS_EMPTY_PATH"
         argType=string  argLen=24
         argHead="{\"path\":\"\",\"content\":\"\"}"
```

⇒ 模型反复发出 `{"path":"","content":""}`（24 字节常量）。

**这是模型侧行为，非 harness 缺陷**，三项判别互证：

1. 全仓 grep 无任何构造该模板的代码；
2. 流式拼装是 delta **累加**（`prev.arguments += …`）：若丢片会得到**残缺 JSON**，
   而实测是**合法 JSON 且长度恰为 24** ⇒ 分片完整；
3. 摘要恒定（3 次运行同为 `7b10e0b7…`）⇒ 与「模型每次发同样字节」一致，
   与「随机丢片」不一致。

**为什么会被硬停**：失败原因恒定 ⇒ 签名恒定 ⇒ 守卫先 Nudge、模型原样重试 ⇒
按设计升级为硬停。**Nudge 在该路径上是送达的**（`brokerBackedHarnessTool.ts:485-488`）。

**唯一仍建议的 harness 侧小改（低风险、非语义）**：让拒绝信息更可操作。
模型收到 `参数校验失败: EXECUTE_TOOL_ARGUMENTS_EMPTY_PATH` 后仍三次原样重发，
说明该信息不足以让它改对。同族一处：`assertExactKeys` 的多余字段分支抛
`EXECUTE_TOOL_ARGUMENTS_UNKNOWN_FIELDS` **不指明违规字段名**（缺失字段那条已指名）。
**报错是模型唯一的纠正信息，其可操作性直接决定自愈率。**

### 空参数真因的**密码学确认**（跨两个工具，两侧 harness 均已排除）

失败路径的 `argsDigest` = `sha256(**原始** arguments 字符串)`（规范化在校验之后）。
逐字节比对候选常量：

| 观测签名（日志原文）| 候选 | 结果 |
|---|---|---|
| `read_file\|sha256:518341a7f82a294570cc3ba8ae0eec8f157d80c390e…` | `sha256('{"path":""}')` | ✅ 逐位命中 |
| `write_file\|sha256:7b10e0b7…cb45dd` | `sha256('{"path":"","content":""}')` | ✅ 逐位命中 |

**不是推断，是摘要反推。** 两侧 harness 均已排除：

| 层 | 检查 | 结果 |
|---|---|---|
| 本仓 runner | grep 模板字面量（`apps/`+`packages/`）| 零命中 |
| 本仓流式拼装 | `prev.arguments += tc.function.arguments` | 累加；丢片会得**残缺 JSON**，实测是合法 JSON |
| 上游 harness | `agent-loop/lib/index.js:520` `parseArguments(block.arguments)` | **直通模型输出** |
| 上游 harness | 同文件 :540 注释 | 「empty input maps to **`{}`**」—— 不是 `{"path":""}` |
| 上游默认值填充 | grep `fillDefaults/applyDefaults/normalizeArgs` | 零命中 |

⇒ `{"path":""}` **只能来自模型**。且**跨两个工具**（read_file / write_file）同形
⇒ 是**通用**退化（必填字符串参数填空串），修复范围应是「空参数」而非某个工具。

**可操作建议**：让拒绝信息带上**字段名与期望形状**（模型收到
`EXECUTE_TOOL_ARGUMENTS_EMPTY_PATH` 后原样重发，说明该信息不足以纠正；
同族 `EXECUTE_TOOL_ARGUMENTS_UNKNOWN_FIELDS` 亦不指名违规字段）。
**产品语义建议**（需裁定）：空必填参数**无害**（空路径不可能写入）⇒
是否给一次「明确要求补全」的早期回路，而非走「提醒→重复→硬停」。**不单方面改守卫语义。**

   ⇒ harness ↔ Broker ↔ Kernel 的机制**健全**；
2. **失败只在「模型走不完工具序列」这一层**（23–31% 任务级），与四项指标无关；
3. **⚠ 此前那组数字是共享库残留造成的，不代表平台** —— 同链同配置换独立库后全部归零。
   **共享开发库的指标不可用**，此处有了实证。

**口径提醒**：②④ 分母为 0 ⇒ **n/a 不是 100%**，是「窗口内没发生」。

### `--hours` 时长驱动**首次真跑**：1 小时 / 58 轮，准时停在截止点

命令：`bash scripts/run_convergence_soak.sh --hours 1 --isolated-db --label hours1`

```
label=hours1      mode=live        driver=hours
runs_done=58      runs_cap=10000   hours=1
started_utc=2026-09-13T18:21:51Z
deadline_utc=2026-09-13T19:21:51Z
elapsed_seconds=3618
pass=44           fail=14
```

**判定：可用。** 三条独立证据：

1. **准时性**：`elapsed_seconds=3618`（60 分 18 秒），距 1 小时截止仅超 **18 秒**
   （最后一轮收尾）⇒ 未跑飞、未提前退出、未卡死；
2. **由时长而非轮数终止**：`runs_cap=10000` 生效中但**从未触及**；
3. **MANIFEST 完整**：`driver / hours / started_utc / deadline_utc / elapsed_seconds`
   全部如实记录 ⇒ 事后可审计，不必猜。

**失败率 24%（14/58）** —— 与合并 30 轮 23%、异构套件独立库 23–31% 一致
⇒ 现有 **4 组独立样本**支撑，可作基线。

**30–100h 外推**（基于本轮实测）：单轮 29–116s、中位约 60s
⇒ 8h ≈ 480 轮、24h ≈ 1400 轮、100h ≈ **6000 轮 ≈ 6 万次模型调用**。
独立库每 58 轮增长到 `goals=15 / attempts=60 / model_invocations=396`。

**建议顺序（不是等待）**：当前 24% 失败的主体是**同一已知形态**（模型发空参数），
直接跑 100h 的主要产出是把已知形态重复观测数千轮，且会淹没
「长稳/时序/租约/恢复」这类真正需要长跑回答的问题。故：
① 先修「可操作报错」（带字段名 + 期望形状）→ ② 用 `--hours 1` 复测看失败率变化
（基线已就位：24% / 58 轮）→ ③ 确认下降再上 8h → 24h → 100h。
工具的入口（`--hours` / `--until` / `--isolated-db` / 失败留现场 / MANIFEST）**已全部实测可用**。

**成本提醒**：100h ≈ 6 万次模型调用；云端需确认配额与费用，
本机 Qwen 无费用但慢 2–3 倍（8 轮实测），该尺度的时程需另算。

## 3.5 P0：live 主路径曾因「从连接器 URL 猜授权」整体不可用（2026-09-13）

真实链条实测暴露的回归，**只有 live 才看得见**（记账单测用替身、CI 被计费阻断）。

**症状**：每轮 2–11 秒即失败，`modelRounds=0`、`got=`（零工具调用）、
`executeErrors=(none)`、`loopError=(none)` —— 外部只看到「模型没跑」。

**二分定位**：`e1971f1`（26 轮 / 89s）→ **`aec2332`（355 批，单独即 0 轮 / 11s）**。

**根因**（用一次性探针插桩取出，未提交改动）：

```
MODEL_INVOCATION_LEDGER_CREATE_HTTP_422:
  {"code":"VALIDATION_ERROR",
   "message":"provider_ref='deepseek:api' 不在冻结 Profile 允许集中"}
```

355 批新增的 `resolveOfficialProviderRef()` **从 `RING_LOCAL_QWEN_BASE` 猜** provider_ref
（含 `deepseek` → `'deepseek:api'`），而该 Goal 的冻结 ModelProfile 允许集里没有它 ⇒ 422
⇒ `createAndDispatch` 抛错 ⇒ 模型一次没跑。**这正是 AGENTS §9 明文禁止的
「连接器 URL ≠ 合同授权」**；而既有 Cordis 路径有正确约定
（`resolveProviderRef`：options → `RING_CHAT_CLOUD_PROVIDER_REF` → `'ring-kernel'`），新代码未沿用。

**教训（值得固化）**：

1. **同一仓内已有正确约定时，新路径必须沿用** —— 否则会重犯文档已禁止的错误；
2. **启动阶段的失败必须可见** —— 该 422 没进任何日志字段，我是靠临时插桩才取到的；
   「被吞的错误」会让修复变成盲修，且表现为误导性的「模型零轮」；
3. **判据要用真实信号**（`modelRounds > 0`、`model_invocations` 有行），
   **不是「测试通过」** —— 测试此前一直是绿的；
4. `--isolated-db` + 复核共享库，二者**都** 0 轮 ⇒ 排除了「库状态」这一常见误判方向。

详见 Issue #70。修复提案已给出（与 Cordis 对齐的一行级改法）。
