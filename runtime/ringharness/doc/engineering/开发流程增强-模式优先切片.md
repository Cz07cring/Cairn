## 1. 为什么要增强流程（书中问题 → 本仓症状）

书的核心判断：**框架会过时，模式不会**；生产级 Agent 卡在协作、预算、重试/持久化、权限与审计，而不是「再调一次 Chat API」。

对照 ringharness 近期摩擦：

| 书中生产问题 | 本仓已出现的对应症状 | 流程上要钉死的习惯 |
|---|---|---|
| 把 Demo 循环当生产系统 | 在 `runActivation` / Control 侧加厚 tool_calls，试图本仓自跑完整 Agent Loop | **循环归 Harness；副作用归 Gateway；DONE 归 Kernel** |
| 单体里工具与编排共址 | Runner 本地读盘 / 假 SUCCEEDED / 盲重试 | 工具只经 Broker；终态只认可信 receipt |
| 崩溃丢状态 | 失租后 DISPATCHED 悬挂、原 Activity 永久 RECOVERING | 失租→UNKNOWN→对账；Stop 屏障后再 READY |
| Workflow COMPLETED 当业务完成 | Temporal/模型成功冒充 Goal DONE | Hermes 证据口径；批次自检表必答 |

增强目标：**不换技术栈，换切片与验收习惯**，让每批都像书里一章——先问题、再模式、后实现、最后对照。

## 2. 模式地图（书 → ringharness，禁止抄框架）

```text
书：Agent Loop (ReAct)          → 本仓：DeepSeek Harness（上游）
书：ToolRuntime / Hooks 准入     → 本仓：Harness 注册 + Kernel/Broker 再鉴权
书：Agent Core 沙箱执行          → 本仓：ExecutionBroker + 工作区/租约
书：Orchestrator + Temporal      → 本仓：GoalWorkflow + Kernel Activities（裁决仍在 PG）
书：LLM Service                  → 本仓：Runner / 本地 Qwen（PM2）；非调度权威
书：预算 / OPA / 审计            → 本仓：Policy + VerificationProfile + Ledger + 屏障
```

**硬翻译（与 Effect Gateway 一致）：**

1. **ReAct 循环不在本仓 Control 内实现完整版。** 本仓实现「一次 activation 的宿主与观察」+ Effect Gateway；多轮 Think→Act→Observe 由上游 Harness 持有（见书第 2 / 32–33 章）。
2. **Temporal 是持久编排，不是业务真相。** Workflow/Activity 完成 ≠ Goal/Task DONE（见书第 21 章 + `doc/v0.6/01`）。
3. **版本门控先于行为分叉。** 新编排路径必须 `workflow.patched` / GetVersion 同类机制，旧历史可重放（本仓已有 `m3-execute-orchestration-v1` 先例）。
4. **工具三阶段：** 准入（gate / authorize）→ 执行（Broker）→ 收尾（receipt / UNKNOWN 对账）；禁止跳过中间态写成功。
5. **超时外长内短：** GoalWorkflow `RunActivation` > Broker/工具 > 模型 `RING_LOCAL_QWEN_TIMEOUT`；禁止内层比外层更长导致白做功。

语言选型上 Shannon 用 Go/Rust/Python；**本仓已裁定 Python 控制面 + TS Runner**（`doc/v0.6/01` §1.1）。吸收的是**职责分离模式**，不是换语言。

## 3. 批次切片协议（替代「想到哪写到哪」）

每个开发批次（Cursor / Codex / OpenCode）在认领时除四方字段外，**必须写满下列「模式卡片」**（可写在 Issue 评论或进度文「本批」段）：

| 字段 | 要求 |
|---|---|
| `problem` | 本批要解的**一个**生产问题（一句话） |
| `pattern` | 对照的通用模式名（ReAct 观察、Effect 咽喉、失租隔离、版本门控…） |
| `owned_loop` | 本批是否触碰 Agent Loop？若是，循环持有方必须是 **Harness**，否则退回 |
| `side_effect_throat` | 副作用是否只经 Step/prepare/(Broker)dispatch/receipt？ |
| `done_authority` | 本批**绝不**写 Goal/Task DONE 的证明方式（测名或断言） |
| `seam` | 可独立红绿的验收缝（单测 / 集成 / live）；禁止「顺手绿一片」 |
| `contrast` | 明确**不做**什么（对照书「框架 API ≠ 模式」） |

### 3.1 推荐切片粒度（书：从第一个工具任务开始）

按依赖推进，**一次只闭合一条缝**：

```text
① 工具参数规范化 → ② Effect Gateway（prepare→终态→ToolResult）
→ ③ 失租/UNKNOWN/对账/Stop → ④ Harness 驱动 E2E（官方 Loop + Gateway）
→ ⑤ 预算/审批/验收屏障 → ⑥ 可观测与长时间跑
```

与 v0.6 M0–M5 对齐时：**M3 优先闭合 ①–④**；未闭合前不开 M4 产品化表面。

### 3.2 禁止的「假进度」形态（书：ReAct 不是正确保证）

- 用 Control 发 tools / 解析 tool_calls 冒充 Harness Loop 已通  
- 用模型成功、shell 0、Activity SUCCEEDED、Workflow COMPLETED 当 DONE  
- 轮询超时本地写 SUCCEEDED  
- 失租后盲再 dispatch（不复用 `effect_id` / 不对账）  
- 为绿测缩减 VerificationProfile 或跳过屏障

## 4. 验收四问（每批自证 + Hermes 复检）

仿书「本章要点回顾」，owner 自证与 Hermes 验收统一答这四问（证据=命令+摘要+退出码）：

1. **循环归谁？** Harness / Runner activation / 本仓自建？（只允许前两者；自建 Loop → 退回）  
2. **副作用咽喉在哪？** 是否只有 Gateway/Broker 路径产生 effect？有无本地读盘捷径？  
3. **失败怎么停？** UNKNOWN / 关闸 / Stop CONFIRMED / 版本门——缺一则说明为何本批不需要  
4. **DONE 有没有被碰到？** 断言 Goal≠DONE；若本批无关 Goal，写明「未触达」  

OpenCode 探针优先验证 1–3；Codex 审计优先查重复副作用与假 DONE；Cursor 合并前四问必须齐全。
