## 2. 已修的「静默降级」（启动器内，均有单测锁定）

1. **模型环境优先级反转**。旧脚本先 source `chat.env` 再 source `qwen.env`，而 `.` 是普通赋值
   ⇒ qwen.env 反向压过 chat.env。改为调用仓库权威 `scripts/runtime_env.py`。
2. **启动器继承调用者 shell 的陈旧模型残留**。残留被当作「进程显式 export」而压过 chat.env
   ⇒ runner 旧模型名 vs ModelProfile 新模型 ⇒ 登记 **422**。改为默认剥离
   `RING_LOCAL_QWEN_*` / `RING_CHAT_*` / `RING_CLOUD_MODE`（覆盖需显式
   `RING_JOINT_ALLOW_ENV_OVERRIDE=1`）。
3. **worker 主体与领取者不一致**。公开读路由按「是否持有该活动」判可见性 ⇒ 不一致时
   runner 读自己的活动得 **404** → `ACTIVITY_GET_FAILED` → PLAN 反复失败。
4. **worker 容量被残留预留吃满**。失败的 activation 按设计把资源预留留在 `HELD` 等对账
   （`record_activation_termination` **不释放资源**）；共用主体时占满 `model_slots`，
   此后一切准入报「**Worker 资源不足以准入该活动**」（实测 8/8 HELD）。故用专属主体
   `joint-arb-worker` + 显式 `RING_WORKFLOW_WORKER_SUBJECT`。
5. **令牌有效期**。control 的 `identity` 硬拒 `exp-iat > 3600`，原先签 8 小时 ⇒ 全 401。

## 3. 已修的真卡点：输出预算 512 对推理模型不够

**现象**：`MODEL_INVOCATION_LIVE_EMPTY`（`kernelModelInvocationHttp.ts:105`）。模型调用登记
`SUCCEEDED`、耗时约 10.9s（确为真实调用），正文为空；PLAN 停在 RUNNING。

**根因**：`deepseek-flash` 与 `deepseek-v4-pro` 均为推理模型，先消耗 reasoning token。
PLAN 的 `max_tokens` 被钉在 512，推理吃满即 `content=""`、`finish_reason=length`。

**复现（直连 api.deepseek.com，同一 PLAN 提示词）**：

| max_tokens | deepseek-flash 空正文 | deepseek-v4-pro 空正文 |
|---|---|---|
| 512 | 0/3 ~ 3/3（随推理量波动） | 3/3 |
| 1024 | — | 1/3 |
| 2048 | — | **0/3** |

`reasoning_tokens` 恰等于上限时必空（如 512/512/514）。用真实 `context_digest` 时 v4-pro 稳定
3/3 空 —— 非偶发，随上下文长度非确定性失败。

**修复**：
- `apps/control/.../settings.py`：新增 `RING_MODEL_MIN_OUTPUT_TOKENS`（默认 2048）。
- `apps/control/.../routes/probe.py`：dispatch 取 `max(登记值, 下限)`，并在空产出时打印
  `finish_reason` / `reasoning_tokens`，使「预算被推理吃光」与「模型真没产出」可区分。
- `apps/runner/.../openaiCompatibleToolChat.ts`：新增 `DEFAULT_MAX_OUTPUT_TOKENS=2048` 与
  `maxOutputTokensFromEnv`；`toolChatConfigFromEnv` 写入 `maxTokens`（此前**无写入方**，
  下游四处 `?? 512` 全部落回 512）。四处默认值统一引用该常量。
- `kernelModelInvocationHttp.ts`：登记值改用 `maxOutputTokensFromEnv(process.env)`，
  避免「登记 512、实耗 2048」的账实不符。

**效果（实测）**：PLAN 由反复失败 → **SUCCEEDED**；EXECUTE 首次被领取并推进到 RUNNING。

## 4. 本轮新增发现（待处理）

### 4.1 执行腿的读取路径不可配（§17 同族）

`executeOfficialRuntime.runOfficialExecuteTurn` 的 `expectedPath` 默认 `notes/execute.txt`，
且**不读** `RING_HARNESS_EXECUTE_READ_PATH`（该旋钮只接在 FSM 分支）——旋钮存在但无读取方。
未提供该文件时受控 read_file 得 `exit_code=2`（无 stdout/stderr），表现为 effect FAILED、
反复重试而 Goal 永不推进。

**当前处置**：由种子把真实盘口写到 `arb_workspace/notes/execute.txt`。修好之后
**read_file 实测 SUCCEEDED / exit_code=0**。
**建议**：把 READ_PATH 接到 diagnose 链路，或让默认值可由 Goal 合同给出。

### 4.2 执行腿租约心跳只续一次

`withOfficialLeaseHeartbeat` 在缺 `RING_HARNESS_EXECUTE_HEARTBEAT_MS` 时直接 `run()`（不心跳）。
补上后实测仍只在启动约 1 分钟后续**一次**（08:17:01 续，租约到 08:27:01，之后不再续），
而间隔本应 30s。长于 TTL 的执行腿会中途丢租约，最终提交必被 409 拒绝。
**待查**：`resolveHeartbeatIntervalMs` 与定时器实现是否只做一次性预续期。

### 4.3 EXECUTE 不收敛到终态

补齐心跳后，EXECUTE 在受控读成功、2 次模型调用成功后仍长时间 RUNNING，工作流一直处于观察循环，
`criterion_verified` 0/1、无屏障。疑似卡在读后阶段（AB08 drain 或封印前置）。

### 4.4 跨活动推进无人负责

`enqueue_ensure_workflow` 全仓**只在 START 时调用一次**（`storage/activities.py:449`）；TEMPORAL
模式下 PLAN 跑完后无组件再起 run 领取 EXECUTE。`orchestration_deliveries` 有 PENDING 投递无人
消费 ⇒ **relay 无进程在跑**。推进本身可行：`RealTemporalClient.ensure_started` 在既有 run 已
COMPLETED 时按默认 `ALLOW_DUPLICATE` 静默开新 run（`client.py:248`），且须传**真实 command_id**
（随机 UUID 时新 run 秒退、不 admit 任何活动）。
