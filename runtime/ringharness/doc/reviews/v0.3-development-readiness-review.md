## RD01 / P1：项目级Skill验收没有可用的审计对象合同

位置：[05:132](../05-API接口文档.md) AuditResource、05:289—291 validate/activate、05:334 outcome、05:373 VALIDATE_SKILL映射。

VALIDATE_SKILL无Goal/Task，其outcome与激活请求要求audit_id；唯一明确定义的AuditResource却必须绑定subject_candidate_manifest_id与goal_contract_revision，CandidateManifest也要求goal_id。未定义Skill专用审计记录、固定验证配置、创建途径及其三态受理规则。不能要求实现者虚构Goal来满足字段，或直接相信worker自报PASS。

建议：新增SkillValidationRecord，明确subject_skill_version_id/content_digest、固定profile或独立验证策略、producer与证据、逐项三态、接收事务和查询入口；激活必须精确匹配待激活版本及有效PASS，无安全阻断。

关闭证据：无Goal的Skill从CANDIDATE到独立验证再ACTIVE完整链路；旧版本audit_id、其他Skill审计、伪PASS、缺项、撤销竞争均拒绝激活。

## RD02 / P1：审计去重键与补证据重审关系未定义

位置：01:317—321；05:132、156、198；08§4与§12。

文档要求“同一已受理审计键仅采纳一次”、INSUFFICIENT可重审、有效FAIL保留，但没有定义该键的字段和审计记录有效性变化规则。若按候选/profile/layer唯一，会拒绝合法补证据；若按attempt唯一，又必须明确多个attempt结果如何形成当前受理集合、重复消息与冲突如何区分。accepted_audit_ids不能替代这套规则。

建议：分别定义不可变审计提交的幂等键、验收槽(profile/layer/criterion)和重审代次；明确同消息重传、同键异内容隔离、旧INSUFFICIENT后补证据、有效FAIL保留、来源被撤销后重新评估的事务与审计记录。补充数据库唯一约束。

关闭证据：INSUFFICIENT→新审计PASS可以合法收敛；同键矛盾阻断；乱序重复不增计数；有效FAIL不被后到PASS覆盖；来源失效有可追溯处理且不能静默删除旧审计。

## RD03 / P1：文字字段边界与Content Schema不一致

位置：05:39规定objective 1—10000、criterion 1—200；05:209规定Epoch≤9223372036854775807；contracts/content-v1.schema.json:1176—1196、3132—3136。

直接调用冻结content_codec.validate，以实际GoalContract字段Schema和FinalizationSubject.write_epoch字段Schema验证，观察：

| 输入 | 文字规定 | 当前Schema/检查器 |
|---|---|---|
| objective="" | 禁止 | 接受 |
| success_criteria=[] | 禁止 | 接受 |
| success_criteria为201个不同ID | 禁止 | 接受 |
| write_epoch="9223372036854775808" | 超BIGINT上限 | 接受 |
| write_epoch="9999999999999999999" | 超BIGINT上限 | 接受 |

Schema中目标仅maxLength、标准仅maxItems=10000，epoch仅19位长度和数字格式，故不只是完整标准库与简化检查器的差别。现有无记录不PASS规则仍在；以上并不证明系统会假DONE，但可能导致非法合同被散列接受、后续数据库拒绝及实现分歧。

建议：明确API→领域→Content的校验责任，统一基础边界并实现领域跨字段检查；生产验证库与文档检查器均覆盖新增边界。还需明确空required_layers、全optional标准和target_scope/layer组合在何处拒绝，不能借空集自动完成。

关闭证据：最小/最大/越界反例在Python、TS及API准入结论一致；合法值hash保持确定；非法值在持久化前拒绝。

## RD04 / P1：SSE事件载荷不是完整的类型化合同

位置：05:389—393；04:40—46。

定义了事件名称和通用envelope，但payload仅写“类型化内容”，没有各type的字段、版本和客户端消费规则。前端要求按entity_state_revision合并，后端可选择补丁、全量资源或失效通知，不同选择无法直接互通。SKILL_REVOKED又是项目级变化，Event.goal_id必填，需要明确向各Goal扇出或独立项目通道。

建议：选定全量/补丁/失效通知策略并定义事件联合Schema、schema_version、项目级变更传播、未知type处理；固定SSE id与seq、重连游标编码关系。

关闭证据：生成客户端无需any；每类事件有fixture；新旧版本、乱序/重复、游标过期及项目Skill撤销能恢复一致视图，且不执行任何业务动作。

## RD05 / P1：验证器合同仍需补到可执行程度

位置：03:24—34；05:63—65、132、156；02§4—5。

已定义verifier_ref/digest与阈值字段、固定必要层，足以约束方向；但未定义批准registry条目的输入输出合同、metric类型解析、运行环境/超时的判定、语义/对抗层评分规则及规则版本如何绑定。Kernel被要求核验逐项结论，尚缺其依赖的结构化VerifierResult。通用reason和evidence_ids无法独自说明机器怎样核验语义结论。

建议：补VerificationRun/VerifierResult与版本化验证器注册合同；定义测量值/单位/证据映射、基础设施失败与业务超限区分、语义评分依据及不确定转INSUFFICIENT的条件。提供机械/语义/对抗/GLOBAL最少各一份具体配置与已标注fixture，阈值在运行前固定。

关闭证据：给定同一固定输入及验证器输出，Kernel判定唯一；已知错误、证据不足与成功样本得到预期三态；语义层用预登记样本评估误判，不把hash或单个模型确信当正确性证明。

## RD06 / P2：旧UX段落仍与v0.3模型审批规则冲突
