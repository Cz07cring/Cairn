## FG01 / P1：已持久化失败VerificationRun在Audit提交前崩溃，缺少确定受理规则

位置：05-API接口文档.md:134、225、242—246、365—366；03-收敛文档.md:132。

VerificationRun按生产attempt分别去重，恢复后可以存在多个run；Audit通过verifier_run_ids引用run，当前汇总描述主要使用已受理Audit。规则没有明确：已经合法保存并含失败观察的run，在生产者尚未提交Audit时，何时由Kernel转换为必须参与汇总的结果，以及outcome能否只引用其中部分run。“有效FAIL保留”原则正确，但从run到有效FAIL的持久转换与完整性校验缺失。

确定的反例序列：A为固定候选/profile/round产生可信失败观察并成功登记run → A在提交Audit前崩溃 → B接管，同一assignment产生通过run → B仅引用自己的run提交PASS。若Kernel只核验B列出的引用，A的有效反证可能被遗漏。现有fixture分类器对两组观察分别得到FAIL/PASS，但这不是运行中已发生假DONE的证据。

修订要求：固定验收集合由Kernel枚举该subject/profile/必要槽的全部已持久可信run，而非由提交者选择。登记run时原子生成其确定逐项判定/未决标志；在未决run完成核对前不能DONE。规定迟到run、不同attempt、来源失效、已完成审计以及最终屏障下在途验证的处理。Audit可以是记录/解释层，但不能隐藏已有反证。

关闭测试：在run持久化与Audit提交之间kill；A失败/B通过；A迟到；重复run；A来源有效/失效两分支。有效反证不被跳过，来源失效有受信依据，崩溃不制造FAIL但已有真实失败不能消失。

## FG02 / P1：证据失效传播未闭合到已激活Skill

位置：05-API接口文档.md:238、248—250、333—335、425；08-工程化结构文档.md:221—225。

Skill激活检查当时有效SkillValidationRecord；后续准入检查Skill撤销。新增EvidenceValidityDecision的传播文字明确了run/audit/release和非终态Goal，却未定义其如何影响SkillValidationRecord和已经ACTIVE的Skill，也未规定是否自动转REVOKED或引入独立有效性状态。

反例序列：Skill验收PASS并ACTIVE → 支撑其PASS的可信来源被判INVALID → 原Skill未收到显式revoke操作 → 新activation/后续dispatch仍可能仅依据ACTIVE且未撤销放行。不能要求运维手动另点撤销才闭合可信性。

修订要求：证据闭包包含skill_validations及依赖该Skill的SkillSet/Activity；受信失效事务立即关闭相关版本新准入（与activate/dispatch排序），明确状态转换和恢复方式。重算期间保持阻断；既有效果按原effect核对，不盲重放或伪取消；如果Skill用于生成已发布结果，按依赖闭包记录发布有效性变化。项目通知只是呈现，不承担安全传播。

关闭测试：激活与来源失效并发、失效与dispatch竞争、已激活Skill的来源撤销、跨Goal使用、通知失败。失效后零新准入，已有动作有界收尾且账本可追溯；修复不静默复活旧版本。
