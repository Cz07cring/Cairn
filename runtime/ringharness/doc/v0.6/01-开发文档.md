# 开发文档：Temporal 持久编排与三权隔离

> v0.6 / DESIGN_REVISION · 2026-09-11。Temporal 技术栈修订，尚未实现、未冻结、未完成运行验收。本文与链接的 v0.5 基线合读：本文明确列出的替换规则优先，其余领域、安全及验收要求全部继承；不把历史“未开始”状态当作当前代码状态。

继承基线：[01-开发文档.md](../01-开发文档.md)。

## 1. 技术栈与范围

完整 V1 范围不变。采用 Python 3.12 / FastAPI / Pydantic / SQLAlchemy 控制面；新增 Temporal Server 与 Python Workflow Worker；TypeScript Runner 通过 Temporal TypeScript SDK 承载 Harness activation；React / TypeScript / Vite 与 TanStack Query 保持。PG、S3、Git、沙箱及观测组件继续保留。

Temporal 只接管持久编排，不替换 Harness，也不自动提供验收。Python Workflow 不直接运行模型、HTTP、SQL或文件操作；所有 IO 进入具名 Temporal Activity。TS Runner 负责模型会话，Python 控制 Worker 不再包一层逐 token 的 TS 进程协调。

## 1.1 Python主导，不新增业务语言

`temporalio`是官方Python SDK包，Python Workflow Worker使用它。Temporal Server作为独立基础服务部署，即便其内部用Go实现，也不要求项目编写Go业务代码。

| 部分 | 语言/依赖 | 边界 |
|---|---|---|
| API、Kernel、账本与验收 | Python | 现有业务实现继续保留 |
| Workflow定义、计时、持久编排 | Python / temporalio | 唯一Workflow实现位置；不能复制到TS |
| Harness Runner | 现有TypeScript；必要的Temporal Activity Worker适配 | 只承接具名activation，不维护第二套Workflow/业务状态机 |
| 工具Broker | Python | 受控执行与可信回执 |
| 用户页面 | 现有React/TypeScript | 无Temporal SDK和调度权限 |
| Temporal Server | 独立服务/容器 | 基础设施，不新增Go源码目录 |

这保留原来的Python后端＋TS Harness/前端结构。TS SDK仅作为Runner领取Temporal任务的传输适配；新增Python temporalio与该适配需共同锁定兼容版本。不能把Python重写成TS，也不能为统一语言而私有重写官方Harness。

暂不采用Python长驻Activity再启动并管理TS子进程的默认方案：它额外引入RPC/子进程恢复和取消协调。若后续需要Python单SDK部署，必须另明确持久Runner服务及幂等启动/查询/停止协议，再用TM04/TM06验收，不能仅用subprocess包装宣称简化完成。

## 2. 唯一权威与边界

| 内容 | 唯一裁决方 | 其他组件能做什么 |
|---|---|---|
| 等待、计时器、运行派发、技术重试、恢复执行位置 | Temporal | Kernel 提供可执行动作及许可；旧 PG dispatcher 对已迁移 Goal 禁用 |
| Goal/Task 状态、计划覆盖、权限、预算、审批、证据与 DONE | Kernel / 业务 PG | Workflow 经幂等命令请求改变；Temporal COMPLETED 不能直接写 Goal DONE |
| 执行权限 fence、write_epoch、资源隔离 | Kernel + Broker | Temporal timeout/cancel 是事件，不证明旧进程停机 |
| 模型会话、Skill 固定版本、角色上下文 | Runner / Harness | 不另立调度，不持业务 DB、签名或对象仓管理员凭据 |
| 工件和审计事实 | Ledger / Auditor / Kernel | Temporal history 只放引用，不作为来源与三态验收替代品 |

保留业务 Activity/Attempt 作为审计与授权记录，不再让其 READY 扫描器自主派发。Kernel 可计算 DAG 依赖与下一步动作，但不自行启动 Runner。状态迁移规则仍在 Kernel；Workflow 消费带版本的准入结果来编排。

## 3. 端到端链路

```text
用户 → API：创建 Goal / START 命令
  → PG短事务：Command + 编排绑定 + outbox
  → Relay：幂等启动 GoalWorkflow
  → Python Workflow：调用 Kernel 准入 Activity，取得动作ID/合同引用
  → Temporal task queue：向具名 TS RunActivation Activity 派发
  → Runner：取得目标 attempt 的执行许可、编译上下文、初始化 Harness
     PLAN：零工具 → 真实模型输出 → PlanCreate 校验
     EXECUTE：工具提案 → Broker准入/执行 → 可信回执/候选
     AUDIT：独立上下文与候选 → 验证器 → VerificationRun
  → Kernel：受理 outcome、写证据引用及事件
  → Workflow：依据已提交业务状态继续、持久等待或请求最终验收
  → Kernel：排空义务/效果/资源 → 封存 → Assessment及全标准检查 → DONE
```

运行中 GoalReview 由 Workflow 持久计时器/进度事件触发，Kernel 用触发键去重创建 AUDIT(target=GOAL_REVIEW)。审查快照绑定合同与计划版本；Planner 消费事实摘要和诊断提案，不读其他角色推理。复盘频率、停滞阈值、最大重规划次数必须配置并纳入预算，不能无限复盘。

## 4. 三种身份与两种 attempt

Temporal Activity 是 SDK 执行单元；业务 Activity 是领域动作，两者不可混用。`temporal_attempt` 仅表示投递/技术重试，不能用它替代业务 `attempt_id`、`fencing_epoch`、execution_round 或 audit_round。

一个稳定业务动作ID绑定一个 Temporal activity key；重放/投递重试使用同一幂等键。只有 Kernel 确认旧执行失效、资源安全隔离及效果可处理后，才能批准新的业务 attempt。Planner/Executor/Auditor使用独立认证身份与隔离环境；task queue 命名不构成权限边界。

## 5. 双写与恢复

1. API 命令与 outbox 同一 PG 事务提交。Temporal 不可用时命令保持待派发；不丢弃，也不返回已执行。
2. Relay 使用稳定 Workflow ID 投递；PG 与 Temporal 无分布式原子事务。投递成功但确认丢失时查已存在执行并校对绑定，不重复 START。
3. Workflow 的 Kernel IO Activity 以 command/action ID 幂等调用。PG已提交但 Activity completion 丢失时，重试只取原结果；不重新消耗预算或生成第二个 effect。
4. 通知只是唤醒，业务结果通过 Kernel 获取；outbox 重复和乱序以ID及版本去重。终态前再次读业务状态，不能只依赖内存通知。
5. 技术错误允许有限退避；业务失败进入 Kernel 决策。RunActivation 初期设置 Temporal 自动重试最多1次尝试，失败后由编排调用核对流程；完成重放安全测试后才能开放更细粒度重试。

## 6. 心跳、停止与资源

Temporal 心跳用于执行存活/取消投递；Kernel 许可续期用于业务授权。一个宿主循环协调二者：Kernel续期失败立即撤销后续工具准入，通知编排；不让任一心跳单独扩大权限。所有续期有截止，使用服务器时间判定授权。

暂停/取消先由 Kernel 关闭工程准入、持久 StopRequest，再经编排唤醒 Runner/Broker 停止。Temporal 取消或终止不代替 StopReceipt。旧进程未知时资源保留 QUARANTINED、费用保持待核对；禁止失租即释放所有资源/预算。清理和 RECONCILE 不随主工作流取消一并丢失，必须由独立受信恢复 Workflow 在受限预算内完成。

## 7. 开发顺序

M0：锁版本、定义[05内部协议](05-API接口文档.md)、完成迁移设计与历史重放样例。
M1：TDD完成 START→outbox→Workflow→Kernel幂等回执，禁止工具。
M2：接通真实零工具 PLAN 的 Harness 与本地 Qwen，禁止fixture生成计划冒充模型结果。
M3：接通 Broker 受控工具、心跳、暂停、失租隔离、UNKNOWN核对。
M4：独立验证/GoalReview/最终屏障与用户界面。
M5：全 T/AT/E、Temporal专项、真实100h及发布候选。

每阶段均要失败测试先行；未通过当前阶段的安全边界，不开启下一阶段执行权限。此顺序不缩减 V1 功能。
