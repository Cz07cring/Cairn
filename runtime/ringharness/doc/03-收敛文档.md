# 收敛文档

> V1 开发规格 v0.5。收敛包含运行、集成、证据与交付收敛；所有规则已纳入设计，运行验证尚未执行。模型/协议分别以 [01](01-开发文档.md)、[05](05-API接口文档.md) 为准。

## 1. 不变量

1. Manager规划、Executor实施、Auditor独立验证；三者都不能直接写DONE。ControlKernel根据固定合同和证据做最终转换。
2. Task DONE必须满足固定VerificationProfile必要层，Goal DONE还必须通过FinalizationBarrier和ReleaseManifest。
3. 工程写入都经Broker登记EffectIntent、权限/审批/预算和write_epoch。HTTP去重不替代业务幂等。
4. hash用于核对实际字节；可信来源由采集链验证；正确性由独立验证器证明。签名或模型总结都不能替代验收。
5. 重试、恢复、审计、重规划、replacement都使用同一Goal总账；不可通过换Task ID清零。
6. UNKNOWN不能穿过Goal完成或取消门槛；系统不保证任意目标成功，但必须保证行动有界、失败可解释。

## 2. 标准覆盖和进展

CriterionCoverage将Goal criterion_id精确映射到task_id+acceptance_id+verification_profile_id。PLAN发布时核对每条必需标准均有承担者；文字相似不等于ID相同；已废弃标准和验证器不能被静默复用。

ProgressRecord={goal_criterion_id,task_acceptance_id,candidate_manifest_id,evidence_ids,verifier_digest,verified_at}。可验证的新事实、根因、通过的标准或有效工件可以构成进展；心跳、token、重复日志不构成进展。覆盖关系只证明计划完整，不能算验证完成。

页面分别显示当前计划必要任务完成数与Goal标准验证数，显示plan_revision变化；不以不断增减的Task分母冒充总目标进度。证据必须注明对应候选/合同/配置；新版本失配时标“需重新验证”，历史不删除。

## 3. 固定验证配置与三态审计

VerificationProfile在执行前由批准registry固定：verifier_ref/digest、required_layers、thresholds、required_evidence_kinds、applicability_rule_ref。三层审计能力均属于V1；每类任务的必要层在合同批准前确定，失败后不允许跳层。Goal最终审核固定GLOBAL验证配置。

| Verdict | 含义 | 后续 |
|---|---|---|
| PASS | 本层必要标准得到当前候选有效证据支持 | 所需层全通过后可推进 |
| INSUFFICIENT | 证据缺失、截断、版本不匹配或环境暂不可用 | 补证据/恢复审计；不能记PASS |
| FAIL | 可复现证据与标准矛盾 | 新执行轮次修复或确认失败 |

机械层检查真实结果、内容/来源、候选/基线/版本；语义层检查需求解决程度；对抗层使用独立边界与holdout测试。Auditor不看Executor推理历史，不持工程写许可。候选审计记录分别存producer_activity/attempt与subject_candidate_manifest_id；周期Critic另存GoalReviewResource及运行快照摘要，不能把审计者与被审者的attempt混淆。

来源验证失败不一定说明代码错误，但必须阻止验收；可标INSUFFICIENT并单独产生安全事件。可信且签名有效的失败测试仍为FAIL。

## 4. 明确重试口径

| 计数 | 归属 / 默认 | 增加时机 |
|---|---|---|
| max_execution_rounds | work_lineage_id / 4，含首次 | 进入新的实现修复轮次；单纯崩溃接管不加轮次 |
| max_audit_attempts_per_candidate | 每候选每必要层 / 3，含首次 | 独立审计启动或恢复；不同层分别计数 |
| max_activity_retries | 每Activity / 3，不含首次 | 失败后重新领取/恢复；同时计入相应审计计数 |
| max_plan_revisions | 每Goal / 10，含首次发布 | 成功发布新计划；无效规划虽不升版仍消耗Activity/资源预算 |
| token/cost/tool/network/wall-clock | Goal或运维budget_scope | 所有实际行动；未知费用保留预留 |

重建模型context不等于重建预算；replacement保留work_lineage_id。人工要求额外实现轮次须更新合同或新目标，不能由模型重命名任务绕过。传输请求重发使用原key/effect，仅计网络/实际费用，不虚增实现轮次。

## 5. 无进展检测与升级

| 信号 | 初始阈值 | 动作 |
|---|---|---|
| 同失败签名 | 连续3次 | 写failure memory，阻止同方法重复，L1 |
| 同工具/输入且无新证据 | 最近5次activation出现3次 | NO_PROGRESS，重编context |
| 补丁A/B往返 | 最近6次补丁有2次完整往返 | L2重新规划 |
| 无验证进展且无有效等待 | 20分钟 | L2，受总预算约束 |
| 某计数/资源预算耗尽 | 达批准上限 | 升级/BLOCKED/FAILED，不擅自放宽 |

等待原因RESOURCE_WAIT/MODEL_WAIT/TOOL_RUNNING/EXTERNAL_RECONCILIATION/PAUSED需有相关Activity/effect、截止时间及唤醒条件。合法长测试遵守自身timeout，不能仅凭20分钟无新工件误判循环。

升级顺序：L0当前本地执行→L1新context（同签名一次）→L2 PLAN Activity重拆→L3独立本地Critic→L4已批准数据/费用的云模型→L5人工BLOCKED。未预授权L4由受信宿主登记ModelInvocation并生成subject=MODEL_INVOCATION审批；Planner仍无任何工具；审批通过不代表效果成功。格式错误最多2次修复；网络退避初始2s、上限60s并抖动，仍受预算。UNKNOWN只走原effect对账，不走盲重试。

## 6. 动态DAG与替换任务

Planner只输出候选图和CriterionCoverage。Kernel验证无环、同Goal依赖、合同范围、标准覆盖和预算后，在expected_plan_revision匹配时提交。已运行合同不原地修改；先停止新动作、排空/对账，再创建replacement并保留lineage。DONE历史不可改，下游只有依赖有效完成才能READY。

最终屏障有效时拒绝发布影响候选的计划。需要修复时只走05§3.6的RECOVER_FINALIZATION：INSUFFICIENT且无有效FAIL选择REVERIFY保持冻结；有效FAIL选择REWORK，排空后ABORTED、新write_epoch和PLAN，待新图发布才开放工程Activity；旧许可、旧ReleaseManifest和不匹配证据均不能继续使用。

## 7. Git与候选收敛

每个EXECUTE ActivityAttempt使用独立worktree。提交验证前由Ledger冻结快照生成CandidateManifest；Auditor在只读副本验证。Git commit之外，还绑定未被commit覆盖但影响执行的锁文件、镜像、submodule/LFS解析内容和验证配置。仅有一个可变目录路径不算候选。

Task DONE只表示其合同验收通过。INTEGRATE Activity持目标集成锁，顺序核对integration HEAD、合并、生成新manifest并重跑集成测试。冲突生成有覆盖关系的修复Task，不能偷偷覆盖另一任务；合并前证据不直接证明合并后正确。只读任务可无Git改动，仍需内容工件和验收证据。

## 8. 最终屏障算法

```text
必要工作与集成完成
  ↓ 同Goal准入锁
关闭ENGINEERING dispatch + write_epoch递增 + Barrier DRAINING
  ↓
排空已登记DISPATCHED写入，核对UNKNOWN、旧Runner与资源
  ↓ 在途工程写入=0 且 UNKNOWN=0
封存最终CandidateManifest → Barrier SEALED
  ↓
FINALIZE Activity：只读候选 + 独立验证临时空间
  ↓
形成ReleaseManifest与GLOBAL审计
  ↓ 短事务复核屏障/epoch/合同/计划/候选/标准/账本
全部通过 → Goal DONE + Barrier RELEASED + journal/outbox
有缺口 → BLOCKED 或显式新epoch重规划，旧许可失效
```

同一scope锁将“写入准入登记”和“关闭准入”排序；屏障前登记的请求可能仍在外部执行，所以必须排空，不靠epoch检查宣称已经停止。任何网络/模型等待不持PG事务。

VERIFICATION scope只能读封存候选、写审计临时目录、调用批准验证器/模型；RECONCILIATION只能查询原效果。已获准费用仍计预算，不能借scope逃避云授权。DONE后可以用受限导出作业读取固定ReleaseManifest，但不能重开工程写入。

## 9. 暂停、取消与未知结果

暂停停止派发并保存，取消停止剩余工作并核对。CommandOperation用于用户命令受理/完成，EffectIntent用于工具真实结果。202仅表示命令登记；网络没有响应时查询原command，不能换key重复取消。

失租回执仍可由可信Broker写入原effect inbox；当前Kernel核对后结算，不能让旧attempt直接写状态。未确认外部效果或进程停止时，暂停/取消保持处理中；不自动回滚已发生效果。人工对账必须提供external_ref和独立证据，不能有“强制DONE”按钮。

## 11. 细节收敛规则

计划候选不立即成为运行图。发布必须绑定当前合同和计划版本，经PLAN outcome进入Kernel；替换任务同时检查传递下游，旧输入上的DONE不能作为新图验收。受影响工作未排空或含UNKNOWN时保留旧图并关闭相关新准入，不持锁等待。合同在PAUSED改变后，恢复先规划，不直接运行原图。

周期GOAL_REVIEW是诊断而非验收PASS；最终GLOBAL审计按所有必需验证配置形成数组，并精确覆盖各自标准。等待截止不随轮询刷新；暂停超时只能升级，不能自行恢复业务。Goal预算耗尽后仅有界RecoveryBudget继续安全收尾，恢复额度不足保留未决结果。这些规则由B04—B06/B08反例测试验收。


## 12. MEA轮次与可信收敛

每次新实现轮次新Executor session，每次Auditor activation新session；同轮执行恢复遵守版本/身份/未决效果核对条件。Manager保留结构化事实连续性，可压缩重建，不能把历史自评作为事实。不同模型/会话仍可能有共同盲点，必须使用独立机械验证与holdout。

基线篡改属于信任失败：隔离本轮候选并阻止验收，同时保留外部效果核对。业务源码正常变更不作基线篡改。Auditor缺证据返回INSUFFICIENT，不能因Manager预期、签名合法或hash一致改判PASS；审计反馈不泄露隐藏答案。C01—C04加入G2/G4门槛。


## 13. 三态到下一步的确定规则

有效FAIL优先于INSUFFICIENT，缺项/无效证据优先于PASS；仅全部必需项有效通过才汇总PASS。安全阻断独立于业务结论，存在时不能DONE。合法完成审计的Activity可以SUCCEEDED且审计结论FAIL，这不是矛盾；没有完成的审计不捏造三态记录。

Manager通过版本化PlanningFeedback接收已受理结果，仅建议补证据/新轮修复/重规划；不能覆盖verdict。旧版本反馈不推进当前状态。反馈登记与Audit/outbox同事务，重复消费去重；暂停时保留反馈不唤醒被禁止活动。执行结束清理推理轨迹，持久保存结构化事实与原始工具证据，避免下一轮依赖旧会话。


## 14. v0.5审计受理与有效性

逐profile/layer/criterion固定验收槽，按05§3.9提交键去重、round补证据，不按最后一条结果覆盖。有效FAIL优先；INSUFFICIENT后新round有效PASS可补齐；不确定/来源失效和安全阻断仍拒绝完成。审计轮次计数与Activity恢复计数分开且全部受原预算约束。

每份profile固定一层；完整Task多层验收须注册对应profile并建立精确标准覆盖，Goal单独GLOBAL。VerifierResult对应正式VerificationRun，由受信宿主采集；Kernel按声明类型比较metric及阈值。timeout是环境失败还是业务不达标由固定规则与独立测量决定，不能凭退出码或自由文本决定。

Skill采用SkillValidationRecord的独立三态流程。来源撤销发生在DONE之后保留历史状态但标发布证据INVALIDATED，禁止继续可信导出；新Goal重新验收。历史“曾完成”与当前“证据仍有效”是两个事实。

## 15. v0.5完成判定补充

先检查项目/对象信任与验证准入屏障，再核验Kernel枚举的全部VerificationAssessment和正式Audit。任一有效FAIL优先；缺正式审计、未结算验证义务、隔离输入或信任阻断均不能PASS。仅全部必要项有效通过、义务排空且版本一致才完成。assessment并不冒充Audit；审计执行未完成不捏造其结论，但已有真实反证仍阻止完成。

来源失效先项目封锁再传播，Skill验收依赖失效自动撤销；发布依赖失效追加INVALIDATED。项目解锁不恢复已撤销版本，也不复活Task/Goal终态。恢复额度不足保持可解释BLOCKED。FG01/FG02及其运行反例加入G2/G4，设计闭合不能代替故障注入。
